# Initial scaffold scope

<!-- describes: src/Application/Emails/**, src/Application/EmailContent/**, src/Application/Synchronization/**, src/Mcp/Tools/** -->

The initial scaffold creates the project boundaries needed for the first release without implementing mail, persistence, retrieval, or MCP behavior yet.

The ASP.NET Core host serves three probes — `/started`, `/health`, and `/alive` — on a listener of their own, on port 8081 unless a deployment configures another, in every environment; `docs/operations/health-endpoints.md` states what each one consults, why they are kept off the port that serves `/mcp`, and how a deployment turns them off or puts TLS in front of them, and `docs/architecture/solution-structure.md` records why the service defaults belong to `Host`. Those defaults wire OpenTelemetry, HTTP resilience, and service discovery. The Aspire AppHost wires the host to a PostgreSQL resource for future persistence work.


## IMAP synchronization status

The first implemented slice covers periodic read-only reconciliation, application-owned IMAP/persistence abstractions, EF Core PostgreSQL mappings, bounded raw MIME content storage, synchronization checkpoints, typed connection validation, and disabled-by-default hosted synchronization that supervises each configured account on a schedule of its own, with per-account and per-folder failure isolation. Each run now also reconciles a bounded window of already-stored mail against the server, so a message deleted remotely stops being served locally — as a tombstone every query excludes or as an erased local copy, per account. An account may now opt into push synchronization, which holds a connection open and starts a pass the moment the server reports a change: one `NOTIFY` subscription covering the account's folders where the server supports it, one `IDLE` session per folder where it supports only that, and polling where it supports neither or where push keeps failing. The backward pass narrows itself the same way, asking a server that reports modification sequences only about what changed since the sequence a completed pass recorded. Deployment-specific secret binding and RAG indexing remain pending; SMTP outbox processing has since landed, and the paragraph on delivery below records it. The MCP protocol surface has since landed as an endpoint that is disabled by default and, once enabled, requires an explicit choice between API key authentication and none at all, together with the `list_emails`, `get_email_content`, `search_emails`, and `ask_mail` tools, their descriptor conventions, and the stable error codes every later tool reuses; [MCP tools](mcp-tools.md) and [MCP endpoint](../operations/mcp-endpoint.md) record them. Client certificates are still pending. What all of that is doing at any moment is now readable without a metrics stack: `mfctl mailbox status` reports each account's phase and the wait its consecutive failures grew, and each mapped folder's durable progress beside the outcome of its last turn, which is what separates a folder with nothing left to fetch from one repeating a batch it cannot get past — [reading what synchronization is doing](../operations/admin-endpoint.md#reading-what-synchronization-is-doing) records the whole answer and what it deliberately never carries. The baseline migration and its apply policy have since landed, and so has the integration-test foundation; the EF Core mappings, constraints, indexes, and transaction behavior this slice introduced are now verified against real PostgreSQL by `tests/IntegrationTests`, which is what the `[RequiresIntegrationCoverage]` markers record the location of.

## Submission status

Mail is sent. An account may declare where its mail would be submitted, and a delivery session opens against that server — connected under the transport rules the account is already judged by, authenticated from the mechanisms it really advertises, and reporting the size bound and the two content extensions it will accept; the type is reachable from the delivery path alone, which a rule over the compiled assemblies asserts rather than assumes. An authored message can now be composed into the MIME a server would be offered, with the headers this system owns rather than a caller: the `From` address is the account's own and the authored contract carries no sender at all, the `Message-ID` is minted from a cryptographically secure half and that account's domain, and every author-supplied field that becomes a header is refused for carrying a line break rather than sanitized — as are an address the server advertised no support for and anything beyond the deployment's configured bounds. Beside them, a send can be written down before anything acts on it: one durable record per message MailFathom has been asked to send, carrying the sending account, the recipients by envelope role with a per-recipient outcome, the stage the attempt reached — including one that means the body went out and the answer never came back — and a reference to the message, which is stored once and read back rather than recomposed. The same authored request arriving twice is refused by a unique index rather than by a check, so it produces one record. On top of the composer, a reply, a reply to all, and a forward can be authored from a message this deployment already holds: the threading identifiers, the recipients, the subject prefix, the quoted history, and the files a forward carries are all read out of the stored copy rather than supplied, an email withheld from tools cannot be answered at all, and what comes back is an ordinary authored message the same composer turns into MIME. What a record is written down for now happens to it: a delivery pass claims a batch of one account's outbox under a durable lease that a crashed process's lease expiry hands back, transmits each send one at a time, and settles the record against what the server answered — per recipient as well as per message, so a mistyped address among five neither stops the other four nor sees them offered the message twice. A transient refusal is deferred with a jittered backoff and a bounded number of attempts, a permanent one is terminal at the first answer, and there is exactly one retry layer because the transmission runs outside the resilience pipeline that opens the session. A send whose server never answered is the one case nothing decides automatically: it stays in the outbox saying so, is claimed by nothing, and waits for a person. A written record is delivered promptly through a bounded signal queue whose refusal is explicit, and the account's own synchronization run drains whatever a signal missed. Each attempt emits a span and each outcome a metric, and neither carries an address, a subject, or a line of what a server wrote. What may be asked for over MCP is still nothing: no tool sends mail. [Mail delivery](mail-delivery.md) records what the session establishes, what the composer decides, what an answer to stored mail is built from, what the record holds, how one is delivered, and what all of them deliberately do not.

## Read side status

Three read use cases have landed, all answered entirely from the local copy and none reaching a mail server.

`ListEmails` answers a mailbox listing with structured filters, a bounded page size, keyset pagination, and per-folder synchronization freshness; [Mailbox queries](mailbox-queries.md) documents its request contract, cursor semantics, and privacy bounds. The `list_emails` MCP tool serves it over the protocol.

`GetEmailContent` answers up to ten emails in one call, each with normalized headers, a bounded plain-text body, optionally a sanitized HTML representation, attachment counts, every attachment re-derived from the stored MIME and described, and — on request — a short-lived signed link that fetches each of those attachments. The count and a shared character budget bound what one call draws out of a mailbox, and attachments are subject to neither because no response carries their octets; a truncated body is always explicit and names which bound cut it, an attachment says whether a link was minted for it and why one was not, an encrypted body is a state of its own rather than an empty one, and a missing or damaged local copy produces a stable per-email failure and a durable repair request instead of an IMAP fetch, leaving the emails beside it readable; [Email content](email-content.md) documents the representations, the bounds, the attachment default, what a link authorizes, the sanitization policy, and the consistency behavior. Stored mail is now assembled into conversations as well, from the message identifiers a message carries and from nothing else: every email `list_emails`, `search_emails`, and `get_email_content` publish names the conversation it belongs to, a read carries the exchange's other messages named rather than reproduced, and a call may name a conversation instead of naming its messages — [the conversation a message belongs to](../architecture/stored-email-schema.md#the-conversation-a-message-belongs-to) records what the schema holds and [MCP tools](mcp-tools.md#the-conversation-a-message-belongs-to) what a caller sees. The `get_email_content` MCP tool serves it over the protocol.

`SearchEmails` answers a bounded, ranked window of emails matching free text, with highlighted snippets cut by PostgreSQL and the same structured filters a listing takes; [Email search](email-search.md) documents its query contract, snippet bounds, and why it publishes a window rather than a cursor. On an instance that has activated an embedding profile the same query is also ranked by embedding similarity and the two orderings are combined by Reciprocal Rank Fusion. The `search_emails` MCP tool serves it over the protocol, and its retrieval-mode field reports which of the two answered each call. A second field reports what semantic retrieval can do on that instance at all, so a lexical answer says whether the deployment never embeds, or embeds and currently cannot: an unreachable provider or an expired credential degrades a search to lexical and states that it did, rather than returning fewer results without saying so.

The read-only tools of the first release are complete, and a fifth has since landed beside them: `list_accounts` publishes the accounts a deployment serves, each under the display name its configuration now requires, so a caller can see which mailboxes exist and name one by either spelling — [MCP tools](mcp-tools.md#list_accounts) records it. The first step towards retrieval has landed: every message's extracted text is now cut into overlapping passages with stable content hashes, stored beside the message and erased with it, so re-deriving an unchanged message costs nothing — [Message chunks](message-chunks.md) records the boundary rules and what the hash covers. The tables a vector will live in have landed beside them: one row per registered vector space and one vector per passage per space, with the width a stored vector may have enforced by the database rather than by whatever writes it, described in [Embedding profiles](../architecture/stored-email-schema.md#embedding-profiles) and [Stored vectors](../architecture/stored-email-schema.md#stored-vectors). The boundary that turns a passage into a vector has landed beside those: a declared chain of OpenAI-compatible endpoints reaching one vector space, with the classification that decides which failures are worth repeating, and a deterministic in-repository generator that proves everything downstream at no provider cost — [Embedding generation](embedding-generation.md) records what a declaration means and what it costs. Mail synchronized from now on is embedded as it arrives, on an instance that has activated a profile: a bounded backlog carries each committed message to a worker that gives its passages vectors, off the mailbox fetch and off every read path, described in [Automatic embedding](automatic-embedding.md). The mail an instance already had is reached too: a bounded, restartable sweep cuts the messages stored before passages existed and embeds everything without a vector under the active profile, repeating so that whatever a refused provider call or a full queue left behind is picked up later — [Embedding backfill](embedding-backfill.md) records what it reaches and what one run may spend. The second kind of provider call has landed beside them and is configured entirely apart from the first: one declared OpenAI-compatible chat endpoint, its model and generation parameters read from configuration, with a truncated or filtered generation reported as an answer that was cut short rather than as a failure to repeat, and each provider's health tracked separately so an unreachable chat model withdraws nothing a search depends on — [Chat generation](chat-generation.md) records what a declaration means and what one call may spend. Both boundaries now meet in `ask_mail`, the fourth tool: a chat model conducts a run over this deployment's own retrieval, answers a question about the mailbox, and cites the stable local identifiers of the emails it drew on, so every claim resolves through `get_email_content` — [Mail answering](mail-answering.md) records what the run may reach and what one response publishes. It is the one tool a deployment may withhold for want of a provider, because it needs both configured and working, and a deployment that cannot answer withholds the descriptor rather than offering a capability that would fail on first use. What one question may spend has landed with it and is the operator's to set: how much retrieved mail may leave the process for one run, how many provider calls and tokens that run may cost, and how many runs and tokens every run of a period may cost between them, with a run that reaches the retrieval ceiling answering from what it has and saying so rather than failing — [Mail answering](mail-answering.md) records each ceiling and what a caller is told when one is reached. The act that turns any of the embedding half on has landed last, and only on the administrative surface: `mfctl embedding activate` counts the passages a run would send, states them as characters and approximate tokens, refuses outright where the estimate exceeds the configured ceiling, and asks before it spends; `mfctl embedding status` answers whether semantic search is working and whether a declaration is still waiting for an activation; and `mfctl embedding cancel-reindex` stops a run an operator has changed their mind about — [administering the embedding profile](../operations/admin-endpoint.md#administering-the-embedding-profile) records all three. MailFathom's own contact book has since landed on the same surface as six tools of its own, taking it to eleven: `list_contacts` and `get_contact` read the people a deployment has written down and every address each of them uses, so an agent can answer who a message is from for somebody who writes from three of them, while `create_contact`, `update_contact`, `delete_contact`, and `promote_contact` write that book — the first tools here that change anything, reaching MailFathom's own database and no mail server — and both `update_contact` and `delete_contact` advertise themselves as destructive, because an amendment states the whole record and drops what it leaves out; [Contacts](contacts.md) records what a record holds and [MCP tools](mcp-tools.md#the-contact-book-on-this-surface) what a caller sees. The book has since gained a writer that is not a caller at all: an account may record the people it corresponds with as its mail is synchronized — the author of arriving mail once it has written often enough, the primary recipients of mail the owner sent, and never a mailing list, a role mailbox, or an address the owner excluded — off unless an owner switched it on and switched on per account, with `promote_contact` and `mfctl contact promote` the one crossing into the half the owner asserted and `mfctl contact delete-collected` the way back out of the whole of it; [Contacts § Collecting contacts from arriving mail](contacts.md#collecting-contacts-from-arriving-mail) records what each folder contributes and what bounds a run. Who may reach which of the eleven has landed over all of them: each tool declares the permission required to call it, a caller is listed only the tools its own credential's grant permits, and a call naming any other is answered as a call naming a tool that does not exist, so a refused caller learns nothing about what it was refused. The contact half sits behind two permissions of its own rather than the mailbox ones, split so that a credential that may look somebody up is not thereby one that may erase them — [MCP tools](mcp-tools.md#what-a-caller-is-offered) states which tool requires which permission, and the use case behind each one asks the same question again with the transport absent.
