# Make a permission a named capability MailFathom publishes, grant it to a user through a role assigned at a scope, narrow it by the credential presented, and enforce it in the use case as well as at the transport

<!-- describes: backend/src/Domain/Access/**, backend/src/Application/Access/**, backend/src/Host/Security/**, backend/src/Host/Configuration/Access/**, backend/src/Host/Api/**, backend/src/Host/Mcp/McpAttachmentDownloadEndpoint.cs, backend/src/Mcp/Tools/** -->

## Context and Problem Statement

Authentication is settled on both protected surfaces and authorization is not. `TransportAccessPolicy` asks two questions of a validated token — is this a subject the deployment serves, and does it carry every scope the entry that trusts its issuer requires — and a caller that answers both reaches everything that surface serves. A credential the operator configured, an API key or a registered client public key, is asked neither, deliberately: writing it into this deployment's configuration *is* the authorization decision. `docs/operations/mcp-endpoint.md` records the consequence in *What a credential decides, and what it does not*, and `docs/operations/admin-endpoint.md` records its own: every authenticated caller may perform every administrative operation, which is why an administrative key is as sensitive as the mailbox credentials it can place, the histories it can read, the spend it can begin, and the mail it can dispose of.

Issue 583 is the gate of issue 590's group, and what it has to settle is not one question but a set of them, each of which a later issue would otherwise decide on its own in an implementation diff: what a permission *is*, whose vocabulary names one, whether the set is closed, how each of the three credential kinds acquires one, what a credential naming none may do, whether the two surfaces share a vocabulary, where the check runs, what a refused caller is told, and whether the accounts a caller may reach belong to this model at all.

Two facts constrain the answer and both were checked rather than assumed.

**The MCP protocol has no place on a tool descriptor to state a required permission.** Checked on 2026-08-15 against the current draft specification: a `Tool` carries `name`, `title`, `description`, `icons`, `inputSchema`, `outputSchema` and `annotations`, and `ToolAnnotations` carries `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint`. Per-tool scope advertisement is an open item of the Authentication Interest Group's Tool Scopes working group and is not in the protocol. An earlier design had each tool declare an OAuth security scheme and a required `mail.read` scope; that predates the settled protocol, and this record supersedes it on the point.

**The same specification does sanction varying the listing by the caller.** It states that the set of tools a server returns must not vary per connection or as a side effect of other requests, and then that it *may* vary by the authorization presented on the request — returning only the tools the caller's granted scopes permit — because credentials are per-request input rather than connection state. So the decision a descriptor cannot carry, the listing can.

One neighbouring question is already settled and is not reopened here. Issue 816 separated the scopes a deployment advertises from the scopes it requires, so `OAuthValidationOptions` carries `RequiredScopes` and `AdvertisedScopes` and `scopes_supported` is no longer the enforcement list read backwards.

**Issue 2305 amends this record in place**, because it is still `proposed`, on the same ground issue 1949 amended ADR 0014. The vocabulary, the two halves, the two places a check runs, and what a refused caller is told all stand. What moved is *where a grant is written and over what it reaches*, and three facts about the shape the record had reached made that the question to answer rather than a refinement to defer:

- **A mail grant was written on each credential**, as `mfctl credential create --permission`, rather than on the person. A policy change cost one edit per credential, a group of people could not be given a grant at all, and a credential that named nothing held the whole mail half — so every name a later release published reached it on upgrade alone, which is how `mailfathom.mail.send` arrived on credentials nobody had touched.
- **Administrators were a second identity system.** `AdminEndpoint:Administrators` held them in configuration, each with its own credentials, grant, wildcard patterns, and `AllowedSourceNetworks`, beside the users the deployment already records under ADR 0014. The two never met: a password was refused on the administrative endpoint, and an assertion's audience kept every credential to one surface.
- **An administrative grant always reached the whole deployment.** Nothing could limit an administrator to one organization or one user, so onboarding a colleague in one company meant handing over every company.

ADR 0014 is not reopened by any of this. An organization is still not a tenant, and a second tenant is still a second deployment; what an organization gains here is the role of a **scope** an administrative grant can be limited to, beside the mail-account membership issue 2014 gives it. Issue 1143 asks the wider identity question for Cases, and this amendment settles the authorization half of it and leaves Case membership there.

**Issue 2340 amends this record in place as well**, on the same ground. Issue 2305 decided that a role lists names and never a pattern, so that no release widens a role, and *Consequences* below records what that cost in the record's own words: a permission a release publishes is usable by nobody until a root writes it into a role. That falls hardest on the one role whose whole purpose is to hold everything. Issue 2340 gives the operator the choice issue 2305 withheld — **a role's list accepts a pattern beside exact names** — so a role widens on upgrade exactly where somebody wrote a pattern to say it should, and nowhere else. The closed vocabulary, the two halves, the three records, the scopes, and the root all stand, and so does the refusal of a pattern on a credential's list, a token narrowing, and an OAuth scope. What moved is stated where it moved, each with its reason: *A role is the operator's list*, the seeded `Administrator`, the root, *Patterns leave the configuration, and return on a role's list*, the last rule of *Nobody grants more than they hold*, and *What issue 2340 changes, surface by surface*.

## Decision Drivers

- **A grant nothing enforces is worse than no grant.** An operator who writes a permission and believes it bounds a credential has been given a false answer, so every name a grant may carry has to correspond to a check that exists.
- **A permission has to be legible to an operator before a request is refused.** The configuration entry is where they meet it, and the refusal they read afterwards has to be reconcilable with what they wrote.
- **Three credential kinds acquire authorization in materially different ways.** A key and a public key exist because somebody wrote them into this deployment's configuration; a token is issued by a server that decides for itself who receives one. A model that pretends the three are the same either asks a key for something nothing can put in it, or lets a token be admitted on the terms of a configured credential.
- **The deployment serves one user's mail.** This is not a multi-tenant service, so the model does not have to express delegation, group mapping, or a policy language, and inventing them would be scaffolding for a shape nobody has. **ADR 0014 has since decided that one deployment serves several users**, so this driver no longer describes the shape being built. What it decided about *this* record survives it unchanged: MailFathom is still not multi-tenant, ownership is not a permission, and the closed set below names no account. What ownership adds is a scoping axis beside the vocabulary rather than inside it, resolved before a query rather than granted on a credential.
- **Root `AGENTS.md` asks for authorization close to the use case as well as at the transport boundary**, so that a second entrypoint — a rule action, a worker, a command, a gateway added later — cannot widen access by omission.
- **What leaves the process is a different question from what the caller can read.** `ask_mail` sends mail content to a model provider, so whether a credential may reach it is a decision about egress and not only about retrieval.
- **A first deployment has to work before it has an authorization model.** This is somebody's own mail server as often as it is an organization's, and the person standing one up is configuring a mailbox and a credential, not a permission set. A design whose first step is an authorization decision is a design most of its users meet as an obstacle.
- **A grant describes a person, not each way they sign in.** Whoever decides what somebody may do is deciding it about that person; restating the decision on every key, key pair, password, and token they hold is a list of copies that drift apart, and it gives a group of people no place to be granted anything.
- **One person is one identity on every surface.** A user the deployment records and an administrator it configures are the same person more often than not, and two identity systems mean two places to revoke somebody and two names an act can be attributed to.
- **An administrative grant has to be boundable to part of the deployment.** A deployment serving several organizations needs somebody in one of them able to administer that one alone, or every onboarding goes through the operator of the whole service.
- **Nobody may grant what they do not hold.** Once administration is delegated, the grant to administer grants is the one that can widen everything else, so it has to be bounded by the grantor's own.
- **A break here would be affordable and would still have to be written down.** ADR 0004 permits a `0.y.z` minor to break the configuration schema, the MCP tool contract and the deployment contract, and requires each break to be named against its surface with the operator's action. So the question the default answers is what serves an operator, never whether the project is allowed to make them act.

## Considered Options

- **A closed set of named permissions this repository publishes, granted on the credential's configuration entry or read from a token's scopes.**
- **Roles: a few named bundles — reader, operator, administrator — an entry selects one of.**
- **An operator's own vocabulary, mapped onto operations in configuration.**
- **Authorize tokens only, through scopes, and leave a configured credential unbounded.**

Issue 2305 weighed where such a grant is written, once the vocabulary was settled:

- **Roles an operator defines as lists of published names — and, since issue 2340, of patterns over them — assigned to a user or a group at a scope, and narrowed by the credential presented.**
- **Keep the grant on each credential, and add a scope beside it.**
- **Grant permissions to a user directly, with no role between them.**

## Decision Outcome

Chosen option: **a closed set of named permissions this repository publishes**, because it is the only one of the four in which every name an operator can write corresponds to a check that exists, and the only one that reaches all three credential kinds without asking any of them for something it cannot carry. **Granted to a user through roles an operator defines and assigns at a scope**, because it is the only placement that writes a decision about a person once, gives a group of people somewhere to be granted anything, and lets an administrative grant stop at an organization or a user, while a list the operator wrote keeps every role exactly as wide as somebody wrote it — a pattern, which issue 2340 admits, being something somebody wrote.

The rest of this section settles each question issue 583 lists, and then each question issue 2305 lists. Every child of issue 590, and every child of issue 2316, is written against these answers, and a child that departs from one says so on its own issue rather than deciding it again. Where a section below was written before issue 2305 and an amended section replaces part of it, the amended section governs and says which part.

### The unit is a permission, and a scope is how a token carries one

A **permission** is a named capability. It is the unit everywhere inside MailFathom: the value an operator writes in a grant, the value a use case checks, and the value a refusal is counted under. It is not a role, because a role this repository defined would be a bundle whose meaning drifts as operations are added to it. **A role in the sense issue 2305 adopts is not a second unit either**: it is a named list of permissions an operator writes, so that one decision about many people is written once, and nothing checks a role — a use case checks the permission the role's list contains. *A role is the operator's list* below states why that list drifts only where its writer asked it to.

An OAuth **scope** is not a second unit. It is the only way a token has of carrying a permission, so where a grant comes from a token, a scope bearing a published permission name grants that permission and nothing else does. A scope naming anything else — `openid`, `profile`, `offline_access`, another resource's scope — is ignored rather than refused, because a token legitimately carries scopes about the client's own session and about resources that are not this one.

`RequiredScopes` keeps the job it has and does not acquire this one. It decides **admission** — whether a caller reaches the surface at all — and a permission decides what an admitted caller may do. A value may not appear in both: a permission name written into `RequiredScopes` would turn a smaller grant into a closed door, refusing at the door a caller the deployment meant to serve less. Startup refuses the overlap. An operator who wants no token admitted without a MailFathom permission already has that, because a token granted nothing is refused on every call it makes.

### MailFathom owns the vocabulary, and the set is closed

The names are this repository's, published here, and validated at startup against this list. A name is an identity that has to survive a rename of whatever implements it, which is the shape this repository writes as a closed enumeration rather than as a plain enum, and a break in one is a configuration-schema break under ADR 0004.

A name is `mailfathom.<surface>[.<subject>].<verb>`, lowercase, dot-separated, and always a valid OAuth scope token so that the same string can travel in a `scope` claim.

| Permission | What it covers |
| --- | --- |
| `mailfathom.mail.read` | The MCP tools that read the local mailbox copy: `list_accounts`, `list_emails`, `get_email_content`, `search_emails`. Not an egress-free grant — see below. |
| `mailfathom.mail.ask` | `ask_mail`, which answers from mail content by sending it to a model provider. |
| `mailfathom.admin.read` | The administrative reads that report the deployment's own state and no mail: embedding status and the activation preview, the loaded rules, a run's progress, and the stopped-job list. |
| `mailfathom.admin.audit.read` | The per-account records derived from mail: the mailbox-mutation audit, the answering audit, the rules history, and the spam classifications. |
| `mailfathom.admin.operate` | Asking the deployment to do work it can already do: running rules over an account, classifying an account, retrying or dropping a stopped job, cancelling a reindex. |
| `mailfathom.admin.credentials.write` | Storing a mailbox refresh token. |
| `mailfathom.admin.spend` | Activating the declared embedding model, which is the one operation that starts a provider bill. |
| `mailfathom.admin.erase` | Erasing the mail stored for a folder an account no longer mirrors. |

The separations above are the ones an operator would plausibly want to grant apart: reading state, reading what was derived from mail, causing work, placing a credential, starting a bill, and destroying mail. That sentence is the rule the set is allocated under, and issue 587 maps every administrative route onto exactly one of these names rather than adding to them.

**`GET /api/admin/session` requires no permission**, and is the one administrative route that does not. It reports the credential the caller already presented and the version the deployment already publishes, so it discloses nothing a caller did not bring; and it is what every command reads first, `mfctl login` included, which refuses to store a credential the deployment has not accepted through it. Putting it behind `mailfathom.admin.read` would make that permission a component of every administrative grant — an operator granting only `mailfathom.admin.spend` could not sign in to use it — which is a trap rather than a separation, and none of the six separations above asks for it. Issue 587's requirement that the route report the caller's grant is unaffected: it reports what the caller holds, which is exactly the question a caller may always ask about itself. Since issue 2305 the route answers only a caller the endpoint admitted, and the endpoint admits a user only while their narrowed grant holds an administrative permission at some scope — so a credential narrowed to nothing, or a user holding no administrative assignment, is answered `401` here as everywhere else on the surface, and what the route adds to its answer is the scopes each permission is held at.

**No permission implies another.** An implication table is a second set of rules to keep true, and writing two names in a grant is cheaper than remembering which one carries which. In particular `mailfathom.mail.ask` does not imply `mailfathom.mail.read` and is not the weaker of the two: a cited answer returns mail content, so the documentation states that granting it is granting access to mail.

**`mailfathom.mail.read` still reaches a provider, and the record says so rather than letting the driver above be read as a promise.** Where semantic retrieval is configured, `search_emails` places the caller's own query text with the embedding provider — `SemanticEmailSearch` asks `ITextEmbeddingGenerator` to embed it, which this repository classifies as `SensitiveContentEgressPoint.HostedEmbeddingInput` and scans before it leaves. So withholding `mailfathom.mail.ask` stops mail content going to a *chat* provider on a caller's behalf and does not make the grant egress-free. Splitting a third permission out of search was rejected: what leaves is the caller's own query rather than mail, the deployment's own switch already decides whether semantic retrieval runs at all, and a permission for it would name a capability an operator turns off in the place it is configured. The documentation states the egress where the grant is described, and the two pages that own the boundary keep stating it.

**A name is published when the capability exists.** `mailfathom.mail.send` is not in the table above and is not reserved here; issue 745 allocates it under this rule when there is a sending tool for it to govern. A grant that names a capability the deployment does not have is a grant that means nothing, which is the thing this record is trying to prevent.

### One vocabulary, two disjoint halves

Both surfaces draw from one published set, and the name says which surface it belongs to. A `mailfathom.admin.*` permission written on the MCP endpoint's grant, or a `mailfathom.mail.*` permission written on the administrative endpoint's, is refused at startup naming the configuration path. One set is one thing to publish, document and validate; the prefix gives the separation without a second registry, and refusing the cross-surface name turns a mistake into a startup failure rather than into a grant the operator believes they made.

**Issue 2305 keeps the halves and moves where they are told apart.** A grant is no longer written on a surface's configuration but on a user, who may reach all three surfaces — the MCP and client endpoints drawing on the mail half and the administrative endpoint on its own — so there is no surface-specific grant left for a cross-surface name to be written on. A role may therefore carry names from both halves, because a person who administers an organization also reads their own mail, and each surface reads the half it guards and ignores the other: a mail name in an administrator's role grants nothing on the administrative endpoint, and an administrative name grants nothing on the MCP endpoint. What stays refused is a name nothing publishes, written in a role or in a credential's narrowing; a scope a token carries is the one place such a name is ignored rather than refused, for the reason given above.

### A grant belongs to the user, through a role assigned at a scope

Issue 2305 replaces what this section decided before. A grant was first written on an `Authentication[]` entry, and then — once ADR 0014 moved credentials out of configuration — on each credential's row, as the names `mfctl credential create --permission` recorded. **A grant now belongs to the user**, and a credential can only narrow it, which *A credential narrows what its user holds* below states.

Three records carry it, and none of them is configuration, because ADR 0014 already placed people and what is decided about them in PostgreSQL:

- **A role** is a name, unique across the deployment, and a list whose every entry is a published permission name or a pattern reaching at least one. A list may hold entries from both halves, for the reason *One vocabulary, two disjoint halves* gives, and a name nothing publishes, like a pattern reaching nothing, is refused when it is written.
- **A group** is a set of users with a name unique across the deployment. A group holds users and nothing else, so no group is a member of another, and it belongs to no organization or to exactly one, as a user does; a group in an organization holds only that organization's members, which is what lets an organization's administrator manage it.
- **An assignment** binds one role to one principal — a user or a group — at one **scope**: the deployment, one organization, or one user. Removing a user or an organization takes every membership and assignment naming it with it, so no grant outlives what it was given to. **Removing a role or a group that is still assigned is refused instead**, naming how many assignments stand in the way, because either would revoke a grant from every person holding it as the side effect of a deletion; the operator revokes first, and the deletion then removes the group's memberships with it.

What a user may do is computed from those records on every request rather than stored on the user, so a change to any of them takes effect at the next request on every replica rather than at the next sign-in; *How a user's grant is computed* below is the whole rule.

**Mail grants are held on the user like administrative ones**, and the scope an assignment names is read by administrative permissions alone. A mail permission reaches its holder's own mail — the accounts ADR 0014 assigns to them — whatever scope the assignment granting it names, because ownership is where ADR 0014 put it and no role reaches another user's mailbox. The scope of such an assignment still decides who may administer it, which is what lets an organization's administrator give a colleague a mail grant.

#### A role is the operator's list, and a release widens it only where somebody wrote a pattern

The *Roles* option below was refused for a reason this amendment keeps: a bundle whose contents a release decides widens every holder whenever a capability joins it, and no amount of configuring makes a holder safe from the next release. **A role here is the operator's list**, so what it holds after an upgrade is still what somebody wrote. Issue 2305 took that to mean names alone and accepted no pattern. Issue 2340 replaces that half, because the objection was never to a role widening: it was to a widening nobody chose. An entry of a role's list is therefore one of two things:

- **A published name**, which grants that permission and nothing else after any upgrade. A release that publishes a permission adds it to no list.
- **A pattern**, in the syntax `PermissionSubtree` already reads: dot-separated segments in which `*` is a whole segment standing for one or more segments, in any position and more than once. `mailfathom.mail.*`, `mailfathom.admin.*.write`, and `*.read` are patterns, and `*` alone reaches the whole published set, both halves. A wildcard inside a segment, as in `mailfathom.mail.c*`, is not a pattern.

**A pattern is stored as it was written and resolved against the published set whenever a grant is computed**, never expanded into names when it is saved. Storing the expansion would have made a pattern a shorthand for typing and left the role waiting on an edit after every release, which is the cost this amendment exists to remove.

**What a role carrying a pattern gains on upgrade is every permission the new release publishes within the pattern's reach**, for every principal holding the role, a group's members included, at every scope it is assigned at, from the first request the upgraded build serves and with nobody writing to the role. What it loses is whatever a release stops publishing there. An operator who wants a role no release can widen writes names, exactly as before.

**A pattern reaching nothing is refused when it is written**, as a name nothing publishes is, because either is a grant nobody enforces. A *stored* pattern that comes to reach nothing — a release retired everything in its reach, or an older build is reading a pattern over names only a newer one publishes — grants nothing and is reported beside the role as an unpublished name is. It is not a failure: the row is a fact about the database, and the build reading it cannot refuse to serve over it.

Reading a role answers with the list as it was written, which is what a replacement sends back, and beside each pattern with what it reaches in the build answering. `mfctl user permissions` and its route name the pattern a permission came through, so a permission nobody typed is still traceable to the entry that gave it.

**The built-in roles are seeded rows rather than definitions this repository keeps.** The release that introduces roles writes them once, as ordinary rows an operator may rename, edit, or delete. No later release edits `Mail user` or `Organization administrator`. `Administrator` is rewritten once, by the migration issue 2340 adds, from every name written out to the single pattern `*` — and only where the row still holds the list it was seeded with, so a role an operator has since narrowed, emptied, or deleted stays as they left it:

| Role | What it lists |
| --- | --- |
| `Mail user` | Every name the mail half publishes in the release that seeds it, which is what a credential naming nothing held before this amendment, so the default a first deployment relies on is reproduced rather than reinvented. |
| `Organization administrator` | The administration of an organization's people and mailboxes: `mailfathom.admin.read`, `mailfathom.admin.audit.read`, `mailfathom.admin.operate`, `mailfathom.admin.credentials.write`, `mailfathom.admin.configuration.write`, `mailfathom.admin.erase`, and `mailfathom.admin.roles.write`. Starting a bill, carrying a mailbox away, and deciding a mailbox's custody are left out, so an operator who wants an organization's administrator to hold them writes them in. |
| `Administrator` | The single pattern `*`: everything both halves publish, in whichever release is reading it. It is the role the default administrator holds, and the one built-in role a later release widens, because holding everything is what it is for. |

`Mail user` and `Organization administrator` stay written out by name, so a permission a release publishes still reaches neither on its own: a mail user gaining every mail capability a release adds is the widening issue 2305 closed, and an organization's administrator is deliberately not given everything the administrative half holds.

**The root is `mailfathom.admin.roles.write` held at the deployment scope, and it is a permission rather than a role.** The escalation rule below needs one: nobody may grant what they do not hold, so without a root a permission a later release publishes would be held by nobody and could be granted by nobody. A holder of `mailfathom.admin.roles.write` at the deployment scope may write any published name, and any pattern, into any role, their own included, which is the one place a grant reaches past what its writer already held. Issue 2305 made that the root *instead of* a role that widens on upgrade, so that every role stayed exactly as wide as somebody wrote it, `Administrator` included, and a capability a release published reached nobody until a root wrote it into a role. Issue 2340 keeps the root and drops the *instead*. A root could always write itself every name, so a root holding `Administrator` as `*` gains on upgrade only what it was already entitled to take, without the edit; and on every other role a pattern is an entry a root chose to write, which is the property the explicit list was protecting. What the root costs is stated rather than hidden — **granting `mailfathom.admin.roles.write` at the deployment scope is granting everything**, because its holder can write themselves any name — so the seeded `Organization administrator` carries the name for use at an organization's scope, where it reaches only that organization's groups and assignments and never a role's definition.

**The last root cannot be removed.** Revoking the last assignment that grants `mailfathom.admin.roles.write` at the deployment scope, taking that name out of the last role carrying it there, removing the last member of a group that is the last holder, and erasing the last user holding it are each refused naming why, because a deployment with no root is one nobody can administer without the database — which *The default administrator* below describes as the recovery path rather than as a way to run. **A role grants the root by name or through a pattern reaching the name**, and each of these refusals counts both: an `Administrator` listing `*` is a holder of the root, and replacing `*` with a list that reaches `mailfathom.admin.roles.write` no longer is refused where that role is the last one carrying it at the deployment scope.

`mailfathom.admin.roles.write` is allocated here, under the rule that a name is published when the capability exists: issue 2314 publishes it with the routes that define roles and groups and write assignments. Reading them is `mailfathom.admin.read`.

### A scope is the deployment, one organization, or one user

**An administrative operation's scope follows from its target.** An operation that names a user, a mail account, a group, or an organization is admitted when the caller holds its permission at a scope covering that target; an operation that names none of them concerns the deployment, and is admitted only at the deployment scope. That decides the question per operation rather than per permission, because several permissions cover both kinds — `mailfathom.admin.configuration.write` both records a user into an organization and rewrites the deployment's persisted configuration — and splitting each of them in two would multiply the vocabulary to say what the target already says.

What each scope covers:

- **The deployment** covers everything.
- **An organization** covers its members, the mail accounts issue 2014 places in it, the groups in it, every assignment whose principal and scope are both within it, and its own display name. Because issue 2014 keeps an assignment inside one organization, every user a mailbox in the organization is assigned to is a member of it, so an organization's administrator acting on a mailbox never acts on somebody outside their scope.
- **A user** covers that user's own record, display name, endpoint switches, credentials, contact book, and assignments made at that scope — and a mail account only while that user is the only one it is assigned to. A mailbox assigned to anybody else is read by them too, and ADR 0014 already decided that what reaches mail other people read is not a single user's to do; an administrator scoped to one person inherits the same line.

Anything in no organization — a user, a mail account, a group — is covered by the deployment scope, and a user in none by a scope naming them as well.

**What is the deployment's alone.** An operation naming no target is the deployment's: the persisted configuration and every read of it, the embedding profile and its activation, the stopped jobs that name no account, the outbox's counts and listing, carrying stored content into the object backend and releasing what a move left behind, cancelling a reindex, and the loaded rules. So are four acts that do name a target but reach beyond it: creating and deleting an organization, and changing an organization's short name, which is a deployment-unique namespace every member's login is spelled in and whose refusal on a collision would tell one organization's administrator which names another holds; defining a role, which writes a vocabulary every organization reads; and writing a group in no organization, or an assignment at the deployment scope. Recording a user or a mail account in no organization is the deployment's for the same reason anything in none is covered by it alone.

Read against the published set, that places each administrative permission:

| Permission | Accepts a narrower scope for | The deployment's alone |
| --- | --- | --- |
| `mailfathom.admin.read` | A user, their record and credentials, a mail account and its synchronization state, an organization, a group, an assignment; every listing answers with what the scope covers | The configuration reads, embedding status and the activation preview, the loaded rules, the stopped jobs naming no account, the outbox's counts and listing |
| `mailfathom.admin.audit.read` | Every read it covers, each naming the user or the account it concerns | — |
| `mailfathom.admin.operate` | Running rules over, classifying, rewinding, and re-deriving an account; a stopped job naming an account; withdrawing or re-queueing a queued message from an account; writing a contact book in scope | Cancelling a reindex, carrying stored content into the object backend, a stopped job naming no account |
| `mailfathom.admin.credentials.write` | A user's credentials, a mail account's refresh token, moving a user between organizations when both sides are covered | An organization's short name |
| `mailfathom.admin.spend` | — | Activating the embedding model |
| `mailfathom.admin.erase` | Erasing a user, a folder's stored mail, a person from a contact book, a user's assignment to a mail account | Releasing the database copies a finished content move left behind |
| `mailfathom.admin.export` | Exporting a mail account | — |
| `mailfathom.admin.custody.write` | Changing a mail account's custody | — |
| `mailfathom.admin.configuration.write` | Recording a user or a mail account into an organization, relabelling and saving a user's record, declaring or withdrawing a mailbox in it, assigning a mail account, renaming an organization's display name | The persisted configuration, creating and deleting an organization, recording a user or a mail account in no organization |
| `mailfathom.admin.roles.write` | A group in an organization and its members, an assignment whose principal and scope are covered | Defining a role, a group in no organization, an assignment at the deployment scope |

`mailfathom.admin.spend` is the one name with nothing on the left. **An assignment's scope bounds every name its role lists, and a name with no operation below the deployment scope is inert below it**: a role carrying `mailfathom.admin.spend` — the seeded `Administrator` among them — may be assigned at an organization or a user, grants its other names there, and grants that one nothing, and a root writing it into a role already assigned narrowly changes nothing at those assignments. Refusing such an assignment was the alternative, and it would make one role assignable at some scopes and not others for the sake of a name that cannot act there anyway. What keeps an inert name from being the grant nobody enforces is that nobody is told they hold it: `mfctl user permissions` and the session route report it as reaching nothing at that scope.

**A scope is not a tenant.** It bounds what an administrator may act on, never what a user reads, and it divides no data: ADR 0014's refusal of multi-tenancy and its answer of a second deployment stand unchanged, and an organization's administrator is somebody trusted with part of one deployment rather than the operator of a separate one.

### How a user's grant is computed

**The grant is the union of what the user's own assignments and their groups' assignments grant**, each assignment contributing every name of its role at its scope. A permission held at several scopes is held at each, and a check asks whether any of them covers the target.

**There is no deny.** A deny turns a union into an ordered evaluation whose answer depends on which rule is read last, and it makes every grant a statement that can be silently cancelled somewhere else — the drift this record exists to prevent, moved from the release to the records. What a deny would express is written instead by not assigning the role, by assigning a narrower one, or by narrowing the credential.

**Groups are not nested.** A nested group makes the members of a group a closure to compute rather than a set to read, admits a cycle, and makes the explanation of why somebody holds a permission a path rather than one row; one level gives every grant an answer of the form *this role, directly or through this group, at this scope*, which is what `mfctl user permissions` reports.

**The credential presented narrows the union, and a token's scopes narrow it again.** A credential naming permissions keeps those of the user's names it lists, and under `PermissionsFromTokenScopes` a token keeps those its scopes carry as well; each narrowing applies to the names and leaves the scope of each one as the assignment gave it. Narrowing a credential by scope is refused rather than left open, for the reason ADR 0014 refused narrowing one within its user's accounts: a second scoping rule beside the assignment is a second rule every check has to keep consistent with the first.

**A user assigned nothing holds nothing.** That is the posture the migration has to preserve rather than the one a deployment meets: issue 2308 gives every existing user an assignment reproducing the union of what their credentials hold, a credential naming nothing counting as the whole mail half as the previous release published it, so no caller gains or loses a permission on upgrade. **Recording a user assigns them `Mail user` at their own scope** unless the request names other roles or none, under the same escalation rule as any other assignment, so a first deployment's person reads their mail the moment they are recorded, and the assignment that lets them is a row read back and removed like every other.

**A client session keeps the narrowing of the credential it was exchanged for**, never a snapshot of the grant. ADR 0023's session recorded the grant at the exchange, so a narrowed grant took effect at the next sign-in; with the grant computed per request, revoking a role reaches an open session at its next request, which is the property a revocation exists for.

### A credential narrows what its user holds

**A credential naming no permission holds what its user holds**, now and after every change to the user's assignments. **A credential naming some holds the intersection** of those with the user's grant: a listed name the user does not hold grants nothing, and is accepted rather than refused because the user's grant moves over time while the credential's list does not, so `mfctl credential list` reports both the list and what it currently yields. **`Permissions` written as an empty list still grants nothing**, which is how a credential is retired without being deleted. No pattern is accepted here: issue 2340 admits one on a role's list and nowhere else. A credential's list, a token narrowing, and an OAuth scope each narrow a grant somebody else decided, and a narrowing that grew on upgrade would be a second place a credential comes to admit more with nobody having written that for it.

That inverts what an unwritten list meant before. A credential naming nothing used to hold the whole mail half, including every name a later release published; it now holds what its user's roles list, and a later release reaches it only through a role somebody writes to.

**A credential carries the surfaces it may be presented on**: the MCP endpoint, the client endpoint, the administrative endpoint, or any combination. A credential states the first two unless written otherwise and the administrative one only when written, so the authority to administer is never acquired by a credential provisioned to read mail. The user's own endpoint switches stay what they are — whether a person is served on the MCP and client endpoints at all — and the two compose: a credential is admitted on a surface only where both allow it. On the administrative endpoint the switch is the user's administrative assignments instead, *Every administrator is a user* below.

**The audience of a signed assertion is kept, and it is no longer what separates surfaces.** A key pair's assertion names the surface it was minted for — `urn:mailfathom:mcp`, `urn:mailfathom:client`, or `urn:mailfathom:admin` — and is refused anywhere else, so one assertion cannot be replayed on a second surface; that is a property of one signed message, which a credential's surfaces cannot give. What keeps a key minted to read mail from administering the deployment is now the credential's surfaces, and that holds for every method alike, where the audience held for one.

**`AllowedSourceNetworks` moves onto the credential**, on every surface. With no administrator left to carry it, the credential is the unit the threat it answers is about — a key that leaks is one key, and a person's workstation key and their scheduled job's key are used from different places. Entries are validated as before, an empty list is no restriction, and a request presenting a valid credential from elsewhere fails authentication with the answer a wrong credential gets. The address compared is the one the forwarded-headers policy resolved, which believes `X-Forwarded-For` only from a named proxy; since a restriction is now a record rather than a setting, startup cannot refuse it, so writing a restriction is refused while no proxy narrower than an address family is named, and startup warns when the configuration has since stopped naming one.

**A client-certificate trust profile still carries no grant.** It decides which machine may reach a surface, ahead of any credential, and admits nobody on its own.

### Every administrator is a user

**A user recorded with `mfctl user add` is the only principal on the MCP, client, and administrative endpoints.** An administrator is a user holding an administrative permission at some scope, and nothing else. A credential whose surfaces include the administrative endpoint authenticates there, and its user is admitted only while the narrowed grant holds at least one administrative permission; one that holds none is answered `401`, exactly as a credential nobody holds, so the endpoint does not tell a probe which people exist.

**`AdminEndpoint:Administrators` goes**, with what each entry carried: its credentials become a user's, its grant becomes an assignment, and its networks become the credential's. `AdminEndpoint:Authentication[]` declares the methods the endpoint accepts in the shape the MCP and client endpoints already use — the method and its transport conditions in the section, the subject in the database — and **a password is accepted there**, under the Basic bounds the other two surfaces apply. A configuration still carrying `AdminEndpoint:Administrators` stops the start, naming the section and the commands that replace it, and nothing is imported: an administrator in configuration has no user to become, which person it was is the operator's to say, and an import guessing it would hand an administrative grant to whichever user the guess landed on.

**The principal an administrative request carries names its user and its credential.** `AuthorizedPrincipal.Caller` stops being a principal with no user: on the administrative surface the caller is signed in as a user exactly as on the other two. What ADR 0014 says about a deployment administrator acting for no user is read accordingly — the administrator is a user, but an administrative operation does not act *for* that user's mail. It reads the deployment-wide catalog its operation needs, bounded by the caller's scope, which is the rule ADR 0014 states per operation.

### Every administrative act names a user and a credential

Every administrative act, every log scope the endpoint opens, every authorization refusal, and every audit record of an administrative act names the user and the identifier of the credential that performed it, and never the credential's material. A user is the unit a person is erased, suspended, and audited as, so an act attributed to a configuration entry's name, as before, was attributed to nobody an erasure or an audit could reach. Where an audit trail outlives the user it names, what it keeps of them is the erasure seam's to state, as ADR 0014 already leaves it for a mailbox's trail.

### The default administrator

**The first start records a user `admin`, in no organization, holding `Administrator` at the deployment scope**, and records that it did. It happens once per deployment: removing `admin` afterwards is final, and nothing recreates it, because a deployment whose operator removed the default account and then found it back with a known password would be worse off than one that never had it. An upgraded deployment receives it on its first start at the release that introduces it, which is how an operator whose administrators were configured reaches the endpoint again.

**`admin` is served on neither mail surface.** It is recorded with both of its endpoint switches off, so no MCP or client caller is ever `admin`, and the roster the single-user startup gate and the provisioning route count — the users a surface admitting a caller who names no user could mean — is the users whose switch for that surface is on. Without that, recording `admin` would put a second user on every deployment: an upgraded deployment serving one person on an unauthenticated MCP or client surface would refuse to start, and a fresh one in that posture would serve `admin` its mail surfaces and refuse to record the person it is for. Counting by the switch rather than exempting `admin` by name keeps one rule for every user — an operator who turns `admin`'s switch on is counting it in, and is refused exactly as a second person would be.

**Its password is read from a setting the host takes from its environment alone**, never from a file or from the persisted configuration, and **applied at most once per deployment**: the first start that finds the setting while `admin` holds no password credential creates one with the username `admin`, presented on the administrative endpoint alone, and records that the setting was applied. Every later start ignores the setting, whatever has happened to that credential since — a disabled credential counts as held, and a deleted one does not bring the setting back — so changing the setting does not change the password, leaving it set discloses nothing the database still accepts once the password was changed, and no route that removes or disables `admin`'s credential can turn the next restart into a sign-in with the shipped value. Without the setting, `admin` exists with no password and nobody can sign in as it until a root provisions a credential for it. Where the username `admin` in no organization already belongs to a different user, the start stops naming the collision, because applying the setting there would either fail silently or sign somebody else in as the root; the operator renames that credential before upgrading.

**The value `admin` is exempt from `UserPasswordPolicy`'s twelve-character minimum, and nothing else is** — not any other value the setting carries, which an operator chose and which is held to the policy like every password: a value that fails it stops the start, naming the policy, rather than leaving `admin` without a password the operator believed they set. The policy's floor exists to stop a password somebody chose being guessed over a listener that can be reached; a value printed in every deployment asset is public whatever its length, so a twelve-character shipped value would protect nothing that `admin` does not, and it would be one more thing typed wrong on a first sign-in. Every other password is held to the policy, `admin`'s own included the moment it is changed.

**Only the assets that publish the administrative listener on loopback ship the value.** The Compose and Quadlet assets publish it on `127.0.0.1` of the host, so the shipped value is reachable only from the machine running the deployment until an operator moves that binding — which is when the warning below matters — and both set the setting to `admin`. **The Helm chart does not set it.** The chart serves `/api/admin` on the Service every pod in the cluster reaches, and keeping the administrative surface off the ingress is a supported posture rather than a mistake, so a known value there would admit any workload in the cluster as the root. The chart leaves the setting unset and documents supplying it from a Secret the operator creates; until one is supplied `admin` has no password, which is the safe half of the trade. The process cannot tell which of these it is in — a container listens on every interface inside its own namespace whatever the host publishes — so the asset rather than the process is where this is decided, and a deployment whose binding already moved off loopback is told what to do under *What issue 2305 breaks*.

**While `admin` still signs in with the shipped value, every start says so.** At each start the stored password credential of `admin` is checked against `admin`, and while it still matches, a warning names the user, says the password is the one every copy of the deployment assets ships with, and names the command that changes it. A refusal to serve was the alternative and was not taken: it would make the first sign-in, which is the only way to change the value, impossible, and whether the listener is reachable from anywhere but the machine is a fact about the operator's network that the process cannot see.

**Recovery is the database's.** An operator locked out of every administrative account deletes `admin`'s password credential row and the record that the setting was applied, and restarts with the setting carrying a new value. That is deliberately not a route, and both halves of it are in the database for that reason: anybody able to delete those rows already holds the deployment's data, and a route that restored access — or a route that could arrange for the setting to apply again — would be one more way in.

### Patterns leave the configuration, and return on a role's list

The `*` patterns `AdminEndpoint:Administrators` accepted leave with it, and no credential or token narrowing accepts one. Issue 2305 refused one on a role as well: a pattern was resolved against the published set on every start, so it widened its holder on upgrade exactly as the unstated grant did, and the need it served — *everything on this surface without listing it* — was to be met at the moment of writing by the seeded `Administrator` list, and after an upgrade by a root writing each new name into it.

Issue 2340 reverses that for a role's list and for nothing else, and the reason is what separates the two widenings. The unstated grant widened a credential because nobody had written anything. A pattern widens a role because somebody holding the root wrote it, into a record that is read back, audited as it was written, and shown beside what it reaches. What the edit after every upgrade bought in exchange was small, since a root may write itself any name, and what it cost was a deployment whose administrator could not use a release's new capability until they had found out it needed granting. *A role is the operator's list* above states the syntax and what an upgrade does to a role carrying a pattern, and *Nobody grants more than they hold* below states who may give one.

### Nobody grants more than they hold

Delegated administration is only bounded if the grant to administer grants is bounded by the grantor's own, so every write that can widen somebody is checked against what the writer holds:

- **Defining or editing a role** is the deployment's alone: it needs `mailfathom.admin.roles.write` at the deployment scope, which is the root, and may list any published name and any pattern reaching one. Every other write below is bounded by what its writer holds.
- **Writing an assignment** needs `mailfathom.admin.roles.write` at a scope covering both its principal and its scope, and every name of its role held by the writer at a scope covering the assignment's — for a mail name, held at all, since its scope is not read. **Revoking one** needs the same coverage and nothing held, because taking a grant away widens nobody.
- **Adding a user to a group** needs `mailfathom.admin.roles.write` covering both the group and the user, and every name the group's assignments grant held by the writer at a scope covering each of them, because joining a group is receiving its assignments.
- **A scoped administrator records users only into their own organization**, and moves a user into, out of, or between organizations only when their grant covers both sides; leaving every organization is a move into the deployment's scope, so only the deployment's scope writes it. **A move out of an organization is refused while the user is a member of any of its groups or the principal of any assignment at its scope**, naming how many, because a group in an organization holds only its members and an assignment left behind would reach into an organization whose administrator no longer covers the user to revoke it. The operator removes them first; the move unassigns nothing on their behalf, as issue 2014's moves do not.
- **A credential cannot widen its user**, since what it admits is bounded by the user's grant whatever it lists — **but it is a way in as that user**, so provisioning, rotating, or enabling one needs `mailfathom.admin.credentials.write` over the user *and* every name the user holds, held by the writer at a scope covering each — a mail name, held at all. Otherwise an organization's administrator could set a password for a member of their organization who holds the root and sign in as them. What the rule cannot remove, and does not pretend to, is that a writer who passes it may sign in as that user and read their mail: placing a credential is the power to act as its user, which is why it is a name of its own and was one before this amendment. Disabling and deleting a credential widen nobody and need the coverage alone.
- **A role listing a pattern is the root's alone to give.** The three rules above bound a write by what its writer holds *today*, and the holder of a pattern comes to hold names no writer held when they wrote: an organization's administrator who passed the rule against today's reach would have given, or acquired, whatever the next release publishes there. So a write that gives a role carrying a pattern, or a way in as somebody holding one, needs `mailfathom.admin.roles.write` at the deployment scope *as well as* everything above. That is **writing an assignment** of such a role, at any scope and to any principal, the writer included; **adding a user to a group** that any assignment gives such a role to; and **provisioning, rotating, or enabling a credential** for a user who holds such a role, directly or through a group. A stored pattern reaching nothing today counts, since a release may publish into its reach. The root is the right holder because it is the one writer a pattern can never outgrow — it may already write any name into any role — and the rule keeps the property that has to survive an upgrade: nobody below the root gives or acquires a role that later holds a name they do not. Comparing the writer's own patterns against the role's was the alternative and was not taken. What a request holds is narrowed by its credential to names, so *holds this pattern* has no answer per request, and a containment rule between two patterns is a second matcher whose every mistake is an escalation. What the rule costs is stated rather than hidden: an organization's administrator cannot give `Administrator`, or any other role carrying a pattern, to a colleague even at their own organization's scope, and cannot set a password for a member who holds one; both go to a root. Revoking such an assignment, removing such a member, and disabling or deleting such a credential widen nobody and need the coverage alone, as before. The refusal names `mailfathom.admin.roles.write` and says it is asked over the whole deployment because the role widens on upgrade, so it is not read as the ordinary refusal of a name held too narrowly.

- **A persisted-configuration write that decides who an endpoint admits needs the root.** `mailfathom.admin.configuration.write` at the deployment scope writes the deployment's persisted configuration, and two parts of it decide admission rather than behaviour: any endpoint's `Authentication` section, and `ReverseProxy:TrustedProxies`, whose answer every credential's source-network restriction is compared against. Emptying an `Authentication` section turns that surface into one accepting no method, whose callers act as `admin` on the administrative endpoint and as the served user on the other two, so without this rule a writer holding the configuration grant alone could hold the root without anybody granting it, and could serve somebody else's mail to anyone who reaches the listener. A write to either part is therefore refused unless the writer holds `mailfathom.admin.roles.write` at the deployment scope, naming that permission, whatever path reaches it — a persisted setting, an edited document, or an adoption of what the files decide. The files themselves stay the operator's: what is written on the host is outside every route.

Assigning oneself is not refused, because it passes the same rule: an administrator can give themselves a role only where they already hold every name in it at that scope, which widens nothing.

### What the deployment advertises is what a client can ask for

`scopes_supported` on a surface whose `OAuth` entry sets `PermissionsFromTokenScopes` carries the whole of the half that surface draws on, and nothing on a surface where no entry sets it. That follows from what the field means: it tells a client what to ask its authorization server for, and a token on such a surface may bring any name of its half. It also tells an operator which scopes to create in their authorization server, read from the document rather than transcribed out of anybody's roles. Advertising the whole half widens nothing, because a token keeps only the names its user's grant holds as well — the grant is the bound, which issue 2305 moved from the entry's configured ceiling onto the user, so there is no configured ceiling left to advertise instead.

A permission name is refused in `RequiredScopes`, for the reason given above, and in `AdvertisedScopes`, because the surface that reads it already advertises it and one that reads none would be telling a client to ask for something nothing here grants. The composition issue 816 settled is otherwise unchanged: a required scope is advertised whether or not anything repeats it, and an advertised scope is never enforced.

### What a grant nobody narrowed holds, and what the startup record says

Before issue 2305 this section decided that an unstated grant was the whole surface: a credential whose entry, and later whose row, named no permission held every name its surface published, including every name a later release published. The reasoning for a permissive default stands — somebody standing MailFathom up for their own mail must not meet an authorization model before they have a working deployment, and an upgrade must not stop a deployment that changed nothing — and what carries it is now different:

- **A credential naming nothing holds what its user holds**, so it stays as permissive as the user it belongs to and no more.
- **Recording a user assigns them `Mail user`**, so a first deployment's person reads their mail without anybody writing an authorization decision, and **the first start records `admin` holding `Administrator`**, so a first deployment can be administered without writing a configuration section.
- **A release that publishes a permission reaches nobody.** No role gains it, `Administrator` included, until a root writes it into one, and the changelog says so beside the capability, in the same reading of ADR 0004 that governs any other operator-visible movement. That is the hazard the old default carried — `mailfathom.mail.send` arriving on credentials nobody had touched — and this amendment closes it rather than documenting it.

**A surface accepting no method still serves its callers**, because refusing to serve it would turn a supported posture into a startup failure. The caller it admits is a user, as every caller now is — on the MCP and client endpoints the one user the startup gate guarantees there is among those whose switch for that surface is on, which never includes `admin`, and on the administrative endpoint `admin` — and **it holds exactly what that user's assignments grant**, with no credential to narrow it. Before issue 2305 this posture granted the whole half; it now grants what the user holds, so a permission a later release publishes reaches it only through a role like everywhere else, and the migration gives a user who held no credential — the user this posture served — the whole mail half the previous release published, so it loses nothing on upgrade. Every administrative act under it is attributed to `admin`. A deployment whose `admin` has been removed serves no unauthenticated administrative caller, and its startup says so. `McpTransportAuthenticationWarning` and the administrative endpoint's own startup warning report the posture as what it is.

An `Authentication[]` list with no entries accepts no credential, on all three endpoints now that the administrative one carries one too, and nothing refuses it: a posture is reported by the startup warning each endpoint carries rather than treated as a mistake.

Three things keep the posture visible, and none of them asks the operator to configure anything:

- **The startup record states what every endpoint accepts and where its grants are read**, says whether `admin` exists and whether it still signs in with the shipped value, and names every credential restricted to source networks while no proxy is named to resolve them. It never names a grant, because a grant is now a record that changes while the process runs; `mfctl user permissions` reads it instead.
- **The session route and `mfctl status` report the caller's grant**: the user, the credential, every permission held with the scopes it is held at, and the narrowing the credential applied. `mfctl user permissions` explains a grant as *this role, directly or through this group, at this scope*, so a surprising permission is traced to the row that gave it.
- **The changelog names every permission a release publishes**, that no role gains it, and that a root writes it into whichever roles should carry it.

**This amendment does break public surfaces, and records each against ADR 0004 below.** The original decision broke none: `Permissions` and `PermissionsFromTokenScopes` were settings an entry could carry, every existing entry stayed valid without them, and issue 590's prediction of a break was what that decision avoided. Issue 2305's breaks are recorded under *What issue 2305 breaks, surface by surface*.

### The accounts a caller may reach are not part of this model

A permission says what a caller may do. Which mailbox it may do it to is a different question, and this record does not answer it.

Not because the two would be hard to combine, but because bounding a caller to particular accounts presupposes a deployment in which more than one caller has a legitimate claim to a different part of the mail — several users, or one user deliberately confining an agent to a corner of their own mailbox. This deployment serves one user's mail, which is a decision driver above rather than a fact about the current release, and *Revisit* below already names a deployment serving more than one user as what reopens the question. Settling the bound now would fix its shape — a list of aliases on a credential's entry — before the question that shapes it has been asked, which is the same mistake as inventing a policy language for a tenant nobody has. **That question has since been asked and answered by ADR 0014**, and the answer vindicates the exclusion rather than reversing it: the bound is not a list of aliases on a credential's entry and not a permission at all, but a narrowing of the account resolution that runs before a mail query, so the shape this record declined to fix is not the shape the answer took.

So no entry carries an account list, the contract the application layer receives says nothing about accounts, and no path narrows the accounts it returns by the caller's identity. Every admitted caller reaches every account the deployment configures, which is what it does today.

Issue 588 held the axis as future work behind a multi-user or multi-tenant decision, which ADR 0014 has since taken. **Nothing remains on it.** The narrower axis that record was read as leaving there — bounding a credential *within* its own user's accounts — is refused by it, and the issue is closed as not planned: a credential reaches every account the user it resolved to owns, and nothing narrows it further. So this record's exclusion is permanent rather than pending, and the two things it preserved stay true of anything that proposes the bound again: that accounts are not permissions, since folding them together would put the operator's own account aliases into a vocabulary this repository publishes; and that a scope has to be applied before ranking rather than after it, so that mail the caller may not see never influences the results it does.

**Issue 2305's scope is not that bound returning under another name.** An assignment's scope says which part of the deployment an administrative permission may be exercised over; it is never read by a mail permission, which reaches its holder's own accounts and nothing else, so no role, group, or scope makes another user's mailbox readable through the mail half. What an administrator at a scope reads of somebody's mail is what the administrative routes already return under `mailfathom.admin.audit.read`, bounded now by the target's place in that scope.

### The transport refuses cheaply, and the use case is the authority

Both checks exist and they are not the same check.

- **At the transport**, authorization runs where `TransportAccessPolicy` runs today, behind the rate limiter, so the partitions and the existing refusals are unchanged. It is what keeps the tool listing honest and what refuses a call without reaching a use case.
- **In the use case**, the check is the authority. An entrypoint added later — a rule action, a worker, a command, a second protocol — reaches the use case without passing the transport, and a check that lived only in middleware is one the new entrypoint forgets. A use case never relies on the transport having already asked.

What the application layer receives is an application-owned contract describing the caller: the configured identity it was admitted under and the permissions it holds. Since issue 2305 that is the user the caller signed in as, the credential that admitted it, and the grant computed for it — each permission paired with the scopes it is held at — so an administrative use case asks *over what* as well as *what*, and a mail use case reads the same permission it always read, at the caller's own scope. Nothing from `System.Security.Claims`, ASP.NET Core, or the MCP SDK crosses that boundary, and no use case learns the credential's kind or material — only its identifier, which an audit record names. A host adapter populates it per request scope.

**Work no caller requested runs under the process's own identity**, which is a distinct kind of principal rather than a caller holding everything. A use case that may run without a caller admits the process identity by name; it must never be admitted by holding a permission, because a principal that passes an ordinary permission check is a caller with everything granted wearing a different label.

**A signed capability is the third principal**, and it is what the attachment download route carries. `GET /attachments/{capability}` answers without a credential by design: the URL holds a ticket this deployment signed, `IAttachmentDownloadTicketReader` verifies it against the key ring, and what it names is one attachment rather than a surface. So the capability *is* the authorization, already bounded to a single object and a lifetime, and the use case behind it is reached under that rather than under a caller who was never identified. It is a principal kind rather than an exception, because writing it as an exception would leave the next capability-authorized route to argue for its own.

A use case reached under none of those three fails rather than defaulting to permitted.

### What a refused caller is told depends on who is reading it

**On the MCP surface, nothing.** A tool the caller's grant does not permit is absent from `tools/list`, which the protocol expressly allows and which is the only place the decision can be stated, since a descriptor has no field for it. No `_meta` extension is invented to say it instead: no client reads one, and a test asserting it would be asserting our own extension. A call naming a tool the caller may not reach is answered exactly as a call naming a tool that does not exist — the same shape, the same code, no new failure identity — because from the caller's side the two are the same fact and a distinguishable refusal would disclose a capability the deployment declined to offer it.

This composes with the availability rule `AskMailAdvertisement` already applies rather than replacing it. A tool may be unavailable, unauthorized, or both; the deployment's own switch is evaluated first, and no grant makes a capability the deployment does not have appear.

A listing that varies by caller may not be published in a way that lets one caller's listing serve another, so any cache scope or shared listing cache the protocol offers is per credential or absent.

Two consequences follow and are accepted rather than worked around. A caller cannot discover that it lacks a permission, which is what the operator reads the refusal metric and log of issue 589 for. And no `insufficient_scope` step-up challenge is issued for a missing permission, even where the grant comes from token scopes and the client could in principle acquire it: the listing already told the client what it may do, and a mechanism available only to the credential kind that can step up would make the surface's behaviour depend on which credential admitted the caller — the drift the shared access policy exists to prevent. The challenge keeps naming `RequiredScopes`, because admission is unchanged.

This settles issue 586's acceptance differently from the way that issue words it. That issue asks for a coded boundary failure naming the permission that would have sufficed; the answer here is the unknown-tool answer and no new code, and the operator learns the permission from the record rather than from the response.

It settles one of issue 745's the same way. That issue asks the tool descriptor to state the required grant "in the metadata the protocol has for it", and the protocol has no such metadata — so the requirement is answered by the listing carrying the decision, and the acceptance item asking for an advertised value to be asserted beside the rest of the descriptor has nothing to assert.

**On the administrative surface, the permission that would have sufficed.** The caller there is `mfctl` in the operator's own hands, so the refusal uses the endpoint's existing safe failure shape and names the one permission, and nothing else: no route inventory, no other credential, nothing about the deployment's configuration. `mfctl` reports it in an operator's terms.

**A scope is told apart from a permission by whether the target is the caller's to know about.** An operation that is the deployment's alone, asked by a caller who holds its permission only below the deployment scope, is refused in the same shape naming the permission and that it is held only at a narrower scope, because nothing about the deployment is disclosed by saying so. **A target outside the caller's scope is answered exactly as a target that does not exist** — the same answer a mail read gives for an account not assigned to its caller under ADR 0014 — because a refusal naming the scope that was missing would tell an organization's administrator that the user, the mailbox, or the organization they named exists elsewhere in the deployment. That settles the acceptance items of issues 2310 and 2311 asking a refusal to name the missing scope: it names it where the operation has no target, and answers *not found* where it has one outside the caller's reach. A listing never refuses: it answers with what the scope covers.

### What this model is not

No group or tenant claim mapping from a token, no nested group, no deny, no delegation or impersonation beyond what placing a credential already is, no policy language, no per-message rules, no bound on which of a user's own mail accounts a caller may reach, no scope a credential narrows, and no permission that varies with the content of a request. A user directory, roles, and groups were on this list before issue 2305 and now exist in the shape above. A later issue that wants one of the rest is proposing a decision this record did not take, and says so.

### What issue 2305 breaks, surface by surface

ADR 0004 permits each of these in a `0.y.z` minor and requires each to be named with the operator's action.

- **Configuration schema — breaking.** `AdminEndpoint:Administrators` is removed, and a configuration still carrying it stops the start, naming the section and the commands that replace it. `AdminEndpoint:Authentication[]` declares the methods the administrative endpoint accepts, `password` among them, in the shape the other two endpoints use. The `*` patterns go with the section. A setting the host reads from its environment alone carries the default administrator's password. *The operator's action*, in this order: **before upgrading**, rename any password credential whose username is `admin` in no organization; **in the same step that moves the deployment to this release**, replace `AdminEndpoint:Administrators` with `AdminEndpoint:Authentication[]` entries that include `password`, and set the default administrator's password — never remove the section without writing those entries, because an administrative endpoint accepting no method serves every caller as `admin`; **on the upgraded deployment**, sign in as `admin`, record each former administrator as a user, assign each a role — `Administrator` where the entry granted the whole surface or a pattern reaching it — provision their credentials with the administrative surface, carry each entry's `AllowedSourceNetworks` onto those credentials, and change `admin`'s password. Nothing is imported.
- **Database schema — additive.** Tables for roles and their permissions, groups and their members, and assignments; the seeded built-in roles; a credential's surfaces and source networks; and the record that the default administrator was written. Every existing user gains an assignment reproducing what their credentials held — and a user holding no credential at all, who could only have been reached through a mail surface authenticating nobody, gains the whole mail half as the previous release published it — so the release is deployable over the previous release's data with no operator action in the database.
- **MCP tool contract — unchanged.** A tool listing still varies by the caller's grant, and the migration preserves every grant, so no caller is offered a different listing on upgrade.
- **Deployment contract — breaking.** The assets under `deploy/` drop `AdminEndpoint:Administrators` and its key file and declare `AdminEndpoint:Authentication[]`. The Compose and Quadlet assets set the default administrator's password to `admin`; the Helm chart sets none and takes it from a Secret the operator names. *The operator's action*: on Compose or Quadlet, change that password with `mfctl` on first sign-in and before moving the administrative binding off loopback — and **where the binding is already off loopback, set the setting to a value of your own before upgrading**, since the first start at this release applies whatever the setting carries; a deployment that keeps the shipped value is told on every start. On Helm, create the Secret before upgrading if `admin` should be able to sign in with a password at all.
- **What an operator meets that is not a schema**: `--permission` on a credential now narrows what its user holds rather than granting, and a credential naming nothing no longer gains a permission a later release publishes. *The operator's action*, when a release adds one: assign a role carrying it, or add it to a role already assigned.

### What issue 2340 changes, surface by surface

- **Configuration schema — unchanged.**
- **Database schema — additive, with one seeded row rewritten.** No table or column changes: a pattern is one more value of the column a role's list already is. A migration rewrites the seeded `Administrator` role's list as the single pattern `*`, only where the row still holds the list it was seeded with. `*` reaches on that day exactly the names it replaces, so no caller gains or loses a permission at this release. *The operator's action*: none where `Administrator` was left as seeded. Where it was edited it is left alone, and an operator who wants it to hold everything replaces its list with `*` themselves.
- **MCP tool contract — unchanged.** A tool listing still varies by the caller's grant, and no grant moves at this release.
- **Deployment contract — unchanged.**
- **The administrative HTTP API — changed.** It is not one of ADR 0004's four surfaces and is recorded as they are, because a client reads it. A role is answered with its patterns, each beside what it reaches, and the entries reported as granting nothing now include a stored pattern reaching nothing; each reason a user holds a permission carries the pattern it came through, or none; and a write refused under the last rule of *Nobody grants more than they hold* answers `403` naming `mailfathom.admin.roles.write` and saying the role widens on upgrade.
- **What an operator meets that is not a schema**: a holder of `Administrator` holds each permission a later release publishes with nobody writing to the role; and a role carrying a pattern — `Administrator` among them from this release on — is given, joined through a group, and signed in as through a newly placed credential by a root alone. *The operator's action*: an organization's administrator who was giving `Administrator` at their own organization's scope, or setting a password for a member holding it, asks a root to, or gives a role written out by name.

### Consequences

- Good, because every name an operator can write corresponds to a check that exists, and a name that does not is a startup failure rather than a grant nobody enforces.
- Good, because the three credential kinds are authorized on terms each can actually carry, and a configured credential can be bounded at all, which today it cannot.
- Good, because nothing here has to be configured to stand a deployment up: a recorded user reads their mail through the `Mail user` assignment recording writes, and the deployment is administered as `admin` from its first start. An existing deployment's mail callers upgrade unchanged; its configured administrators do not, which *What issue 2305 breaks* records.
- Good, because the listing decision has protocol sanction and the tool descriptor is left as the protocol defines it, so nothing here has to be unwound when the Tool Scopes working group settles.
- Good, because the use-case check makes an entrypoint added later safe by default rather than safe by the author remembering.
- Neutral, because one closed vocabulary spanning both surfaces is one register to publish and validate, and a role carrying names of both halves is read by each surface for its own half.
- Neutral, because every admitted caller reaches the accounts assigned to its user under ADR 0014, and nothing in this model narrows that further.
- Bad, because the safe configuration is the one an operator has to go and find. The permissive default is the deliberate price of a deployment that works before it is governed, and the startup record, the session route and the documentation are what keep the posture visible rather than implicit.
- Bad, because an operator whose authorization server cannot mint custom scopes cannot use `PermissionsFromTokenScopes`, and narrows each token's credential instead — which means the deployment rather than the authorization server decides what each admitted subject may do.
- Good, because a decision about a person is written once, on the person or on a group they belong to, and every credential they hold follows it; a revocation reaches every credential and every open session at its next request, on every replica.
- Good, because one person is one identity on all three surfaces, so they are erased, suspended, and audited once, and every administrative act names somebody an audit or an erasure can reach.
- Good, because an administrative grant can stop at an organization or a user, so onboarding a colleague in one company no longer hands over every company.
- Good, because a permission a later release publishes reaches no role an operator wrote out by name, so an upgrade never widens a credential on its own; the hazard the previous default carried is closed rather than documented, and where a role does widen it is because a root wrote a pattern saying it should.
- Good, because a first deployment is administered as `admin` on its first start, with no configuration section written by hand.
- Bad, because a permission a release publishes reaches a role written out by name only once a root writes it in, so for those roles a new capability waits on one edit after every upgrade that adds one; that edit is the price of such a role never widening on its own. Issue 2340 removes the wait for `Administrator`, and for any role an operator gives a pattern reaching the new name, and leaves it everywhere else.
- Bad, because a role carrying a pattern is the root's alone to give, so delegated administration stops short of it: an organization's administrator cannot give `Administrator` at their own organization's scope, or place a credential for a member holding it. A rule comparing the writer's patterns against the role's would have allowed both and was refused as a second matcher on the escalation path.
- Neutral, because a pattern's reach is decided by the build reading it, so during a rolling upgrade two replicas answer differently for a permission only the newer one publishes — which is true of that permission's routes as well, pattern or not.
- Neutral, because the root is a permission — `mailfathom.admin.roles.write` at the deployment scope — whose holder can write themselves any name, so granting it there is granting everything, and the documentation has to say so wherever the name is described.
- Bad, because `mailfathom.admin.configuration.write` at the deployment scope is still the power to redefine the service everybody is served by — a model provider, a ceiling, a surface switched off. The parts of it that decide who an endpoint admits are held to the root; the rest is not escalation but is not small either, and the documentation names it as such wherever the name is described.
- Neutral, because which operations accept a narrower scope is decided by each operation's target rather than by its permission, so a reader asks the route rather than the vocabulary; *A scope is the deployment, one organization, or one user* tabulates the answer per permission.
- Bad, because the administrative endpoint now accepts a password, and the Compose and Quadlet assets set a known one. Their loopback binding, the Helm chart setting none, the setting applying at most once, the warning on every start, and the policy applying to every later value are what bound it, and none of them stops an operator who exposes the listener and ignores the log.
- Bad, because placing a credential remains the power to act as its user, mail included; the escalation rule stops it reaching a user who holds more than the writer, and cannot stop it reaching one who holds less.
- Bad, because an operator upgrading from configured administrators re-creates each of them by hand, and a deployment that removed `admin` and lost every other administrator is recovered only through its database.
- Bad, because an administrative refusal for a target outside the caller's scope reads as *not found*, so an organization's administrator who mistyped an identifier and one who named somebody else's user are told the same thing.
- Bad, because a caller refused on the MCP surface learns nothing, so diagnosing a client that stopped working requires reading the deployment's own record rather than the response.

## Validation

- Startup refusals are unit-tested per arrangement: a permission name written into `RequiredScopes`, a permission name written into `AdvertisedScopes`, and `PermissionsFromTokenScopes` on an entry carrying a key or a public key. Each asserts the configuration path in the message, including the entry's index. A name nothing publishes is refused where it is written — in a role or a credential's narrowing — and a test asserts each. Beside them a test asserts the arrangements that are *not* refusals and what each resolves to: a credential naming nothing holds what its user holds, a surface accepting no method holds what the user it serves holds, and an explicitly emptied narrowing reaches nothing. Issue 2305 replaced the cross-surface refusal and the absent-key reading this item pinned before, since no grant is written on a surface's configuration any more.
- Issue 585 adds a rule to `Boundaries.UnitTests` keeping `System.Security.Claims` out of `Application` and `Domain`. That project holds no such rule today and needs one, because `ClaimsPrincipal` ships in the shared framework and `Application` references only `Domain` — so it is the one type of the three the caller contract could name with the build staying green. ASP.NET Core and the MCP SDK are already unreachable there by project reference.
- Per-tool and per-route tests cover the listing with and without each grant, the call refused as an unknown tool, the administrative refusal naming its permission, and a use case refusing an unauthorized principal directly, with the transport absent.
- The refusal metric and log of issue 589 are what an operator observes the boundary through, and the redaction contract is asserted over them beside the rest of the telemetry surface.
- `docs/operations/configuration-reference.md`, `docs/operations/mcp-endpoint.md`, `docs/operations/admin-endpoint.md`, `docs/features/mcp-tools.md` and `docs/operations/mcp-client-oauth.md` state the vocabulary, the grant, what an entry that writes none holds, and what each surface tells a refused caller. The pages that walk somebody through a first deployment say that a credential naming nothing holds what its user holds, that recording a user assigns `Mail user`, and that `admin` is the first sign-in, because a posture nobody is told about is one nobody chose. Issue 2305 replaced the earlier wording of this item, which said a credential reaches the whole surface until its entry narrows it.

Issue 2305 adds what its children are held to:

- A unit test asserts the grant computation: the union of a user's own and their groups' assignments, each narrowing in turn — the credential's list and a token's scopes — and that a mail permission reaches the holder's own mail whatever scope its assignment names.
- A unit test per scope kind asserts what it covers, including that a user scope reaches a mail account only while that user is its only assignee, and that an organization scope reaches no account, user, or group outside the organization.
- A unit test per administrative route family asserts that a target outside the caller's scope is answered as one that does not exist, and that an operation the deployment holds alone is refused below the deployment scope naming its permission.
- A unit test per escalation rule asserts its refusal: a role defined below the deployment scope, an assignment wider than the writer's scope or carrying a name the writer does not hold there, a group membership that would hand over more than the writer holds, a credential placed for a user holding more than its writer, a user recorded outside the writer's organization, a user moved out of an organization while a membership or an assignment there remains, and a persisted write to an endpoint's `Authentication` section or to `ReverseProxy:TrustedProxies` by a writer who does not hold the root.
- A unit test asserts that a holder of `mailfathom.admin.roles.write` at the deployment scope may write any published name into a role and that a holder at a narrower scope may define no role at all, and that the last root cannot be removed by any of the four writes that would remove it; a test over the migrations asserts that no migration after the seeding one writes to a role's permissions.
- A unit test asserts that a role carrying `mailfathom.admin.spend` assigned below the deployment scope grants its other names there and that one nothing, and that the session route reports it as reaching nothing.
- A unit test asserts the bootstrap: `admin` recorded once and never again after its removal, the password setting applied at most once and never again after `admin`'s credential is disabled or deleted, the start stopped by a username collision, the warning while the shipped value still verifies, and the policy exemption applying to the value `admin` alone, any other value failing the policy stopping the start, and `admin` counted by neither mail surface's roster while its switches are off.
- A unit test asserts that a configuration carrying `AdminEndpoint:Administrators` stops the start naming the section, and that a credential is refused on a surface it does not list, an assertion still being refused under any audience but its surface's.
- A test asserts that every administrative act, log scope, refusal, and audit record names a user and a credential identifier and never credential material.
- The migration of issue 2308 is tested to leave every existing caller with exactly the permissions it held before it.

## Pros and Cons of the Options

### A closed set of named permissions this repository publishes

A permission is a name MailFathom defines and enforces. A configured credential is granted a list of them; a token either carries them as scopes or is granted a list beside its entry.

- Good, because a name and a check are introduced together, so the set cannot contain a grant that does nothing.
- Good, because it covers all three credential kinds without asking a configured key for a scope it can never hold.
- Good, because the names are a contract that can be documented once, validated at startup, and advertised to a client that has to ask an authorization server for them.
- Neutral, because it makes this repository responsible for a vocabulary an operator has to create in their own authorization server before a token can carry it.
- Bad, because adding a capability means allocating a name in a published set, which is a contract change rather than a local decision.

### Roles: a few named bundles an entry selects

An entry names one of `reader`, `operator`, `administrator`, and the bundle's contents are decided here.

- Good, because it is the smallest thing to configure and the easiest to explain.
- Neutral, because the initial contents would look much like the table above, grouped.
- Bad, because a bundle's meaning drifts: every capability added later joins some role, silently widening every credential that holds it. Before issue 2305 the chosen option widened an unstated grant the same way, and the difference was that there the operator could stop it — a grant they wrote was a grant a later release never added to — whereas a role's contents are never theirs, so no amount of configuring makes them safe from the next one. Issue 2305 closed that widening: a credential naming nothing now holds what its user's roles list, and a release adds to no role — to no role written out by name, since issue 2340, a role carrying a pattern widening because its writer said it should, which is the configuring this option never offered.
- Bad, because the separations that matter here cut across any small set of bundles. Reading state and reading mail-derived history, or causing work and starting a bill, land in the same role unless the roles multiply until they are permissions with a worse name.

Issue 2305 adopts roles in a different shape and keeps both objections against this one. Its roles are lists an operator writes over the permissions above rather than bundles this repository defines in their place, so the separations survive inside any role and a release adds nothing to one except through a pattern its operator wrote — which, since issue 2340, is what the seeded `Administrator` lists.

### An operator's own vocabulary, mapped onto operations in configuration

The operator invents names and writes a mapping from each name onto the operations it covers.

- Good, because it fits an authorization server whose scope names are already fixed by something else.
- Bad, because the mapping is a second configuration surface with its own errors, and it is exactly where a typo produces a grant nobody enforces.
- Bad, because nothing can be published: `scopes_supported` cannot advertise names the deployment invents per installation, and no documentation can state what a permission means.
- Bad, because a refusal cannot name a permission usefully when the name is per deployment.

### Authorize tokens only, and leave a configured credential unbounded

Keep today's reading — a configured credential's authorization is the act of configuring it — and build permissions only for OAuth.

- Good, because it changes nothing for existing deployments — which was true of the chosen option as first decided, whose unstated grant left them exactly as they were, and stopped being true with issue 2305, whose breaks *What issue 2305 breaks, surface by surface* records.
- Neutral, because it would satisfy the deployments whose clients all authenticate with tokens.
- Bad, because it leaves every key-authenticated caller where it is, and the administrative surface is where that costs most: an API key is what `mfctl` signs in with wherever no `OAuth` entry is configured, so the surface that stores mailbox credentials, starts bills and erases mail would go on granting each of those to any key that can read the session route.
- Bad, because it makes what a credential may do depend on how it authenticates, which is the drift `TransportAccessPolicy` was written as one shared judgement to avoid.

### Roles an operator defines, assigned to a user or a group at a scope, narrowed by the credential

Chosen by issue 2305.

- Good, because a decision about a person is written once and every credential they hold follows it, and a group gives many people one place to be granted anything.
- Good, because an assignment's scope bounds an administrative grant to an organization or a user without a second vocabulary.
- Good, because a list is exactly as wide as somebody wrote it: a release widens no role written out by name, and one carrying a pattern, which issue 2340 admits, only within the reach its writer chose.
- Neutral, because three records — roles, groups, assignments — replace one column, and explaining a grant takes a query rather than reading a row; `mfctl user permissions` is that query.
- Bad, because evaluation reads several records per request, so it is cached per user and invalidated across replicas, which issue 2307 builds.

### Keep the grant on each credential, and add a scope beside it

- Good, because it is the smallest change from the shape that shipped.
- Bad, because a policy change stays one edit per credential and a group of people still has nowhere to be granted anything.
- Bad, because a scope on a credential is a second scoping rule beside the user's, which ADR 0014 refused for the accounts axis on exactly that ground.
- Bad, because a credential naming nothing would keep gaining every name a release publishes, or would need a role-like default to stop it — the roles this option set out to avoid.

### Grant permissions to a user directly, with no role between them

- Good, because it needs no role record and every grant reads as one list.
- Neutral, because it fixes the per-credential copy, which is the worse half of the problem.
- Bad, because a group still needs a list of its own, which is a role by another name, and changing what a kind of person may do stays one edit per person.
