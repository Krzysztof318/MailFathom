# MailFathom third-party license register

This file records the license review for the third-party components MailFathom actually pins, bundles, runs, or calls. It is a review register: it names components, states the terms verified for them, and records a compatibility decision. It reproduces no license text and grants no rights of its own, and it is not legal advice.

It describes software in use and nothing else. A planned, evaluated, or rejected component has no row here, because a row asserts a completed review of something that exists in the repository today.

Four documents describe MailFathom's licensing, and each answers a different question:

| Document | Question it answers | Status |
|---|---|---|
| `LICENSE` | Which rights MailFathom grants for its own code | The unmodified Apache-2.0 text. Never edit it: GitHub detects the license by matching that file, and an edit turns a detected `Apache-2.0` into `NOASSERTION`. |
| `NOTICE` | Who originally created the work, which section 4(d) asks a derivative distribution to preserve | Present, and informational only. Third-party notice text belongs beside it in the bundle below, never inside it. |
| `THIRD_PARTY_LICENSES.md` — this file | Which third-party components MailFathom uses, under which terms, and whether those terms fit both distribution models | Maintained here. |
| A generated third-party notice bundle | The full license texts and attribution notices that must travel with a distributed binary, container, or source artifact | Not produced yet. Issue #191 owns generating it from each artifact's resolved dependency graph; the obligations it must satisfy are the ones recorded in this file. |

The register is deliberately not the notice bundle. A notice bundle is generated from the resolved dependency graph of a specific artifact and contains verbatim license texts; this file is the human decision record behind it, and it exists whether or not an artifact has been built.

A redistribution therefore carries three separate things: the project grant in `LICENSE`, the original-author attribution in `NOTICE`, and whatever notices the components below require. Never merge third-party notice text into `NOTICE`, because that would attribute third-party work to MailFathom's author.

`0.1.0` has been released, so the redistribution obligations recorded here are outstanding rather than anticipated: every component the container image and the Helm chart carry has been distributed, and the notice bundle issue #191 owns is a live obligation against a published artifact rather than a task ahead of the first one.

## License acceptance policy

MailFathom must remain compatible with both contemplated distribution models:

1. commercial closed-source distribution; and
2. open-source publication of the MailFathom project.

A third-party component may be used only when its license permits both, without forcing MailFathom itself to be distributed under a copyleft license.

Allowed licenses include permissive OSI-approved licenses such as MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, PostgreSQL License, and similarly permissive licenses after review.

Licenses that require review before use include LGPL, MPL, EPL, Unicode, custom commercial licenses, source-available licenses, dual licenses, preview license terms, and any license with field-of-use, redistribution, network-service, data-use, patent, trademark, telemetry, or attribution conditions that are not already understood for this project.

Prohibited without explicit owner approval are strong copyleft or source-available licenses that could conflict with closed-source commercial distribution or require relicensing MailFathom, including GPL, AGPL, SSPL, BUSL, Commons Clause, PolyForm Noncommercial, and similar restrictions.

A permissive SDK license never approves the hosted service, model, container image, or trademark behind it. Those terms are reviewed separately and recorded separately.

[ADR 0016](https://github.com/Krzysztof318/MailFathom/blob/main/docs/decisions/0016-third-party-licence-obligations-per-artifact.md) states how a component in the review-before-use band is decided, and the three rules it adds are what the rows below are written against. The unit of review is `(component, version, artifact)` rather than the repository, because a redistribution obligation attaches to what is handed to somebody else; the exposure sections below are the coarse form of that, and a component carrying a condition is decided against the artifact rather than against its section. A component that resolves but reaches no artifact is **latent**, which is a decided state rather than a pending review: its row says so, names the event that makes it live, and states what is then owed. And a conditioned component stays **separately replaceable** — unmodified, its own file in the artifact, never merged into MailFathom's own output, trimmed, rewritten, statically or ahead-of-time linked, or sealed in a bundle a recipient cannot open — with the component dropped from an artifact whose build shape cannot allow that, rather than the condition waived for it.

## How the inventory is produced

Two questions decide every row here, and they are answered separately. **What earns a row** is a decision this repository took: a component it **pins** in a manifest, **invokes** from a script, a workflow, or a skill, **calls** by name from a published artifact at run time, or **ships** — inside an artifact, or as the runtime an artifact published here is written to run on. Something a contributor installs on their own machine, that this repository neither pins nor invokes nor ships, gets no row: an editor, a language server, a shell, a container desktop, a recommended editor extension. Usefulness earns nothing, and neither does being named in a setup document — prose that helps a contributor configure their machine describes that machine, while a row asserts a completed review of a version this project chose and would notice going stale. A row for software nobody here decided is worse than no row, because it makes the absence of a row unreadable. Where the two readings pull apart — a tool a document recommends but no script runs — the rule decides and the prose stays: it keeps its version and its reasoning, and stops promising a row.

**What a row costs** is decided by exposure, which is what the rest of this section is about. A package that ships inside the product carries redistribution and notice obligations; one that only runs on a build agent or a developer machine does not. That distinction is derived from the repository rather than assumed, which is why the sections below are ordered by exposure and why each was produced by a command that can be repeated:

```bash
# Direct pins and the transitive closure they resolve to.
cat backend/Directory.Packages.props
jq -r '.dependencies[] | to_entries[] | select(.value.resolved != null) | "\(.key) \(.value.resolved)"' \
  backend/src/*/packages.lock.json backend/tests/*/packages.lock.json | sort -u


# License expression, license URL, and upstream repository, from each package's own published metadata.
curl -s "https://api.nuget.org/v3-flatcontainer/<id-lowercase>/<version>/<id-lowercase>.nuspec"

# What is actually redistributed: the assemblies a framework-dependent publish of the host emits.
dotnet publish backend/src/Host/Host.csproj -c Release -o <output>
ls <output>/*.dll

# Upstream license of a component that is not a NuGet package.
gh api repos/<owner>/<repo>/license --jq '.license.spdx_id + "  " + .html_url'

# The client stack's direct pins, and the licenses of the closure they resolve to.
cat frontend/package.json frontend/src/*/package.json
pnpm --dir frontend licenses list

# License expression and upstream repository, from a package's own published metadata.
curl -s "https://registry.npmjs.org/<name>/<version>" | jq -r '.license, .repository.url'

# What a bundle actually carries, which is the production closure and nothing the workspace installs to build or test.
pnpm --dir frontend licenses list --prod

# The JavaScript census: how many packages under each term, and every one of them that is not MIT.
pnpm --dir frontend licenses list --json | jq -r 'to_entries[] | "\(.value | length)\t\(.key)"' | sort -rn
pnpm --dir frontend licenses list --json \
  | jq -r 'to_entries[] | select(.key != "MIT") | .key as $terms | .value[]
           | "\($terms)\t\(.name) \(.versions | join(" "))"' | sort

# The desktop shell's direct pins, and the license every crate the lock file resolves declares for itself.
cat frontend/src-tauri/Cargo.toml
cargo metadata --manifest-path frontend/src-tauri/Cargo.toml --format-version 1 --locked \
  | jq -r '.packages[] | "\(.license // "UNDECLARED")\t\(.name) \(.version)"' | sort

# The crate census, and which of those crates a Linux desktop build links out of the graph Cargo resolves for every
# target it knows about.
cargo metadata --manifest-path frontend/src-tauri/Cargo.toml --format-version 1 --locked \
  | jq -r '.packages[].license // "UNDECLARED"' | sort | uniq -c | sort -rn
cargo tree --manifest-path frontend/src-tauri/Cargo.toml --locked --target x86_64-unknown-linux-gnu \
  --edges normal --prefix none --no-dedupe | sed 's/ (\*)$//' | awk 'NF >= 2 { print $1 }' | sort -u
```

Both client enumerations answer for the machine they run on, which is a property to state rather than a defect to correct. `pnpm licenses list` reads what is installed, so it names the platform-specific optional packages this machine selected — one `lightningcss-*`, one `@tauri-apps/cli-*`, one `@rollup/rollup-*` — and not the ones another platform would take instead; the terms are the package's own either way, so a per-platform binary changes which file is installed rather than which licence applies. `cargo metadata` is the opposite and names every target's crates at once, which is why the `cargo tree` line beside it exists: the difference between the two is the difference between what Cargo resolved and what a Linux build links.

`AppHost` and `IntegrationTests` carry no lock file, because the Aspire SDK selects part of their graph from the host platform's runtime identifier. Their packages are pinned centrally like every other project's and are recorded below from `backend/Directory.Packages.props` and the project files instead.

## The client's two dependency closures

The client brings two graphs this register had never carried a shape for, and both are orders of magnitude larger than anything the service pins: 249 packages behind the pnpm workspace, and 499 crates behind the desktop shell's three direct pins. Everything below decides how those are recorded, and it is written here once rather than restated in each of the rows below that depend on it.

**The granularity is a direct pin per row and a census per closure, and the reason is what a row asserts.** Every other row in this file names a component this repository *chose* — somebody read its terms, decided it was allowed, and wrote down what a distribution then owes. A transitive closure is mostly packages nobody chose: `scheduler` arrives because React depends on it, and `foldhash` because something under Tauri does. Giving each of those a row of its own would put seven hundred and forty-eight assertions of a completed review into a file where a row *means* a completed review, and it would bury the twenty-nine decisions that were real — twenty-six npm pins and three crates — under the consequences of taking them. Giving the closure no record at all is the opposite failure, because the terms that travel with an artifact are the closure's terms rather than the direct pins'. So each closure is recorded as a census — how many packages resolve under which terms, with every distinct term named and every package carrying a condition named individually — and each direct pin keeps its row. A package under a permissive, unconditional term is counted rather than named, because counting it is the whole of what its terms oblige; a package under anything else is named, reviewed, and decided, because that is what a row does. A census is checkable: the commands above reproduce it, and a number that no longer matches is a graph that moved.

**Naming follows the package identifier rather than the project's own capitalisation.** The client rows write `react`, `react-dom`, `vite`, `typescript`, `prettier`, and `vitest` because those are the names a manifest, a lock file, and a registry use, and `scripts/update-dependencies.sh` reads this file by matching them. A row headed *ReactDOM* is a row the survey reports as missing.

**What each census currently says**, read from the committed lock files — the JavaScript one on 2026-08-31 and the Rust one on 2026-09-01, when the credential store the desktop head keeps a password in was pinned:

- **The JavaScript closure resolves 249 packages at 258 name-version pairs**, and every one of them declares terms — the census has no unknown bucket. 192 are MIT. The rest are Apache-2.0 (21), ISC (12), BSD-2-Clause (8), BSD-3-Clause (6), `Apache-2.0 OR MIT` (2, the Tauri CLI and its native binding, taken under MIT), MPL-2.0 (2), MIT-0 (2), BlueOak-1.0.0 (2), CC0-1.0 (1), and CC-BY-4.0 (1). **No package in the closure is offered under a strong copyleft or source-available licence** — no GPL, LGPL, AGPL, SSPL, BUSL, Commons Clause, or PolyForm term appears anywhere in it — **and the only weak copyleft in it is the MPL-2.0 pair**, which is a build tool. That is the finding, recorded rather than left as silence, because a closure this size returning nothing is exactly the result a reader would otherwise take for a review nobody performed.
- The four terms that are conditional at all are each decided in the row of the pin that brings them: **MPL-2.0** for `lightningcss` and `lightningcss-linux-x64-gnu`, **CC-BY-4.0** for `caniuse-lite`, and **BlueOak-1.0.0** for `minimatch` in the build-tooling row; **CC0-1.0** for `mdn-data` and **BlueOak-1.0.0** for `lru-cache` in the test-only row. **MIT-0** — `@csstools/color-helpers` and `@csstools/css-syntax-patches-for-csstree`, reached through jsdom's colour parsing — is named here rather than in a row, because it is MIT with the attribution condition removed and obliges strictly less than the majority term already does.
- **What a bundle carries is three packages, all MIT**: `react`, `react-dom`, and `scheduler`. `pnpm --dir frontend licenses list --prod` returns exactly those, which is the mechanical form of the claim the redistributed row below makes — everything else the workspace installs builds, lints, or tests, and reaches no artifact.
- **The Rust closure resolves 499 crates** beside this repository's own `mailfathom-desktop`, which is the one entry `cargo metadata` reports with no licence because it is not published. 312 offer `MIT OR Apache-2.0` in one spelling or another, 109 are MIT alone, and 11 more are `Unlicense OR MIT`, all taken under MIT. The complete tail is in the desktop shell's row below, which is where each of them is decided.
- **293 of those 499 are what a Linux desktop build actually links**, over normal dependency edges for `x86_64-unknown-linux-gnu`. The rest are another target's — the macOS and Windows families — or a build dependency the binary does not carry. All five MPL-2.0 crates are inside the 293, so the review that row records is a review of something an artifact would really contain rather than of a crate Cargo merely resolved.

**A census is a completed reading and not a derived value, which is what decides who maintains it.** `scripts/update-dependencies.sh` surveys both families of direct pins and rewrites them on `--apply`, and it never writes a line of this file — so a moved client pin resolves a new closure whose census nothing recomputes. The run says so when it moves one, and re-running the two enumerations above is part of the same change rather than a task after it.

## Called on the machine an artifact runs on

Neither pinned nor bundled: a library the operating system already has, which a published artifact reaches on the
machine it runs on rather than carrying. Nothing here is restored or carried inside any artifact. Two shapes of that
sit below and their obligations differ, so each row says which it is: a library resolved by name at the first call,
which a machine without it simply does not have, and a library the build links against and the artifact then requires,
which is the LGPL's own shared-library case rather than a dependency that can be absent. A platform's own API — the
Win32 functions `mfctl` reaches for the same purpose, or anything else in the runtime a head is written to run on —
earns no row: it is the operating system rather than a component this project chose.

## Trademark and brand use

This section reviews something none of the tables above covers. A license grants rights in *code*; a trademark protects
a *name*, and the two are decided separately — which is what the acceptance policy means by saying that a permissive SDK
license never approves the trademark behind it. Where an owner below also supplies MailFathom with something, its row in
a table above decides that separately and says so, and each row's *where* column below names every place its marks
appear. What put most of them here is that three pages describe somebody else's product to a reader who has one.
[Configuring a mailbox at your provider](https://github.com/Krzysztof318/MailFathom/blob/main/docs/users/mailbox-providers.md)
tells a reader which address and credential their own mail service publishes,
[connecting the chat client you already use](https://github.com/Krzysztof318/MailFathom/blob/main/docs/users/mcp-clients.md)
tells them where their own chat client's connector dialog is and what it will accept, and
[MCP client OAuth](https://github.com/Krzysztof318/MailFathom/blob/main/docs/operations/mcp-client-oauth.md)
walks the identity provider's side of an OAuth connection with one provider's console named throughout. A page about
interoperating with something has to say what that something is.

**What MailFathom does is nominative use** — naming a product in a true factual statement in order to describe
interoperating with it. Every owner reviewed below either permits that explicitly or is silent on it, and the ones that
address it attach the same conditions: the mark is used as an adjective in front of a common noun, it never appears in
the name of the naming party's own offering, the use must not imply affiliation, endorsement, sponsorship, or
certification, and several ask for an ownership acknowledgement. Nothing reviewed permits a logo without written
permission, and none is used.

**Where the acknowledgement is published, and why there.** The several owners who ask for one are answered by an
enumerated statement at the foot of the page that names the marks, not by a line in `NOTICE` and not by this register.
`NOTICE` was considered and rejected: it is Apache-2.0 section 4(d) attribution for MailFathom's own authorship, and
third-party text does not belong in it. This register was considered and rejected too — it is a review record, and an
acknowledgement that appears only in a review record is published to nobody. The page footer is where the marks are
actually read, it is carried by both the repository and the documentation site, it enumerates the owners rather than
gesturing at them, and it cannot go stale silently: a section added for a new mail service is a mention with no
acknowledgement behind it, which is what the operational rule at the foot of this file now refuses.

None of the above is legal advice, and none of it is a claim about what nominative-use law permits — it is a record of
what each owner publishes and of what MailFathom decided to do about it.

## Open obligations

A second condition of that shape belongs to a service rather than to a license and is recorded with it below: GitHub Pages may carry this project's documentation as a showcase and may not become the delivery surface of a commercial offering built on MailFathom, which likewise decides where the documentation is hosted rather than how the code is distributed. The application icon is licensed to MailFathom by nobody, because it was assigned rather than licensed, and it ships under the project's own grant like the rest of the repository. ## Operational rules for future changes

- Keep package versions pinned centrally in `backend/Directory.Packages.props`, and regenerate the committed `packages.lock.json` files in the same change. Do not use floating versions.
- Add or update a row here whenever a dependency, service, protocol SDK, container image, generated asset, or externally sourced code sample this repository pins, invokes, calls, or ships is introduced, upgraded, replaced, or removed, and none for anything else a change merely names or a contributor installs; § *How the inventory is produced* is what decides which of the two a component is. Record the exact name, version, license expression, upstream source, and any attribution or notice handling.
- A component under *Called on the machine an artifact runs on* records the name a published binary loads it by rather than a version, because the repository pins none: what is installed is the operator's distribution's decision, and a version recorded here would describe the machine that wrote the row. Everything else in the rule above still applies to it, and the row states which terms were reviewed and what would reopen them.
- Put a component in the section that matches its exposure. A component that ships obliges more than one that only builds, and guessing which is which is what this structure exists to prevent.
- Record only what the repository uses today. A component that is planned, evaluated, suggested, rejected, or merely named somewhere does not belong here in any form, because a row states that a review was completed and a review of something not yet adopted would have to be redone at adoption anyway. Keep that reasoning where the future work is tracked — an ADR or an issue — and add the row in the change that actually introduces the dependency.
- Do not merge a dependency with unknown, missing, custom, source-available, copyleft, or service-only terms until the owner explicitly approves the risk.
- Treat model provider terms, cloud service terms, container image terms, and trademark terms as separate from SDK licenses.
- Naming a new owner's product anywhere in the repository is a trademark review, however small the mention. Add a row to *Trademark and brand use* stating what that owner publishes and what MailFathom decided, and put the acknowledgement where the mark is read rather than in `NOTICE`; a mention that arrives without both is the defect, not the mention.
- Never add a logo, a badge, or a screenshot of another party's console, product, or documentation. Each needs that owner's written permission, and no row above records one.
- Preserve third-party copyright notices and license files in source and binary distributions whenever the upstream license requires it.
- Repeat the inventory commands above before a release. A register that was accurate at the previous release is evidence about that release, not about this one.
