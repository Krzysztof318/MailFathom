# MailMcp third-party license register

This file records the license review for the third-party components MailMcp actually pins, bundles, runs, or calls. It is a review register: it names components, states the terms verified for them, and records a compatibility decision. It reproduces no license text and grants no rights of its own, and it is not legal advice.

It describes software in use and nothing else. A planned, evaluated, or rejected component has no row here, because a row asserts a completed review of something that exists in the repository today.

Three documents describe MailMcp's licensing, and each answers a different question:

| Document | Question it answers | Status |
|---|---|---|
| `LICENSE` | Which rights MailMcp grants for its own code | Not present yet. Issue #113 owns the choice of license and the file. |
| `THIRD_PARTY_LICENSES.md` — this file | Which third-party components MailMcp uses, under which terms, and whether those terms fit both distribution models | Maintained here. |
| A generated third-party notice bundle | The full license texts and attribution notices that must travel with a distributed binary, container, or source artifact | Not produced yet. Issue #113 owns the packaging mechanism; the obligations it must satisfy are the ones recorded in this file. |

The register is deliberately not the notice bundle. A notice bundle is generated from the resolved dependency graph of a specific artifact and contains verbatim license texts; this file is the human decision record behind it, and it exists whether or not an artifact has been built.

MailMcp is pre-release, so nothing here has been distributed yet. The redistribution obligations are recorded now because the first release is what makes them due, not because they are already outstanding.

## License acceptance policy

MailMcp must remain compatible with both contemplated distribution models:

1. commercial closed-source distribution; and
2. open-source publication of the MailMcp project.

A third-party component may be used only when its license permits both, without forcing MailMcp itself to be distributed under a copyleft license.

Allowed licenses include permissive OSI-approved licenses such as MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, PostgreSQL License, and similarly permissive licenses after review.

Licenses that require review before use include LGPL, MPL, EPL, Unicode, custom commercial licenses, source-available licenses, dual licenses, preview license terms, and any license with field-of-use, redistribution, network-service, data-use, patent, trademark, telemetry, or attribution conditions that are not already understood for this project.

Prohibited without explicit owner approval are strong copyleft or source-available licenses that could conflict with closed-source commercial distribution or require relicensing MailMcp, including GPL, AGPL, SSPL, BUSL, Commons Clause, PolyForm Noncommercial, and similar restrictions.

A permissive SDK license never approves the hosted service, model, container image, or trademark behind it. Those terms are reviewed separately and recorded separately.

## How the inventory is produced

Exposure decides what a component obliges. A package that ships inside the product carries redistribution and notice obligations; one that only runs on a build agent or a developer machine does not. That distinction is derived from the repository rather than assumed, which is why the sections below are ordered by exposure and why each was produced by a command that can be repeated:

```bash
# Direct pins and the transitive closure they resolve to.
cat Directory.Packages.props
jq -r '.dependencies[] | to_entries[] | select(.value.resolved != null) | "\(.key) \(.value.resolved)"' \
  src/*/packages.lock.json tests/*/packages.lock.json | sort -u

# License expression, license URL, and upstream repository, from each package's own published metadata.
curl -s "https://api.nuget.org/v3-flatcontainer/<id-lowercase>/<version>/<id-lowercase>.nuspec"

# What is actually redistributed: the assemblies a framework-dependent publish of the host emits.
dotnet publish src/Host/Host.csproj -c Release -o <output>
ls <output>/*.dll

# Upstream license of a component that is not a NuGet package.
gh api repos/<owner>/<repo>/license --jq '.license.spdx_id + "  " + .html_url'
```

`AppHost` and `IntegrationTests` carry no lock file, because the Aspire SDK selects part of their graph from the host platform's runtime identifier. Their packages are pinned centrally like every other project's and are recorded below from `Directory.Packages.props` and the project files instead.

## Open obligations

Every component above resolves to MIT, Apache-2.0, BSD-3-Clause, or the PostgreSQL License, all of which the acceptance policy allows, with one exception that changes nothing about distribution: the Claude Code CLI the `Claude review` workflow installs on a runner is proprietary software used under Anthropic's own terms. It is executed rather than linked, and no artifact carries it. Nothing here blocks the first release on licensing grounds. Two obligations are live and owned elsewhere:

- The BSD-3-Clause and Apache-2.0 components in the redistributed set, and the Aspire service-defaults template, require their notices to travel with an artifact. Issue #113 owns the notice bundle that satisfies this, and issue #123 owns the container image that carries it.
- `Aspire.Hosting.EntityFrameworkCore` stays on a prerelease pin until a stable build exists. Recheck its license when moving to one.

## Operational rules for future changes

- Keep package versions pinned centrally in `Directory.Packages.props`, and regenerate the committed `packages.lock.json` files in the same change. Do not use floating versions.
- Add or update a row here whenever a dependency, service, protocol SDK, container image, generated asset, or externally sourced code sample is introduced, upgraded, replaced, or removed. Record the exact name, version, license expression, upstream source, and any attribution or notice handling.
- Put a component in the section that matches its exposure. A component that ships obliges more than one that only builds, and guessing which is which is what this structure exists to prevent.
- Record only what the repository uses today. A component that is planned, evaluated, suggested, rejected, or merely named in a specification does not belong here in any form, because a row states that a review was completed and a review of something not yet adopted would have to be redone at adoption anyway. Keep that reasoning where the future work is tracked — a specification, an ADR, or an issue — and add the row in the change that actually introduces the dependency.
- Do not merge a dependency with unknown, missing, custom, source-available, copyleft, or service-only terms until the owner explicitly approves the risk.
- Treat model provider terms, cloud service terms, container image terms, and trademark terms as separate from SDK licenses.
- Preserve third-party copyright notices and license files in source and binary distributions whenever the upstream license requires it.
- Repeat the inventory commands above before a release. A register that was accurate at the previous release is evidence about that release, not about this one.
