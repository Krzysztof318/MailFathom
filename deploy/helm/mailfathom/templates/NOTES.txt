Watch it become ready:

  kubectl --namespace {{ .Release.Namespace }} rollout status deployment/{{ include "mailfathom.fullname" . }}

MailFathom verifies the database schema while starting and refuses to serve against one it does not recognize. It never
applies a migration itself, in any environment, and neither does this chart: a hook Job would be the automatic
migration that arrangement prevents, and an initContainer would run one apply per replica. If the pod reports a pending
migration, back up {{ .Values.database.name }}, read the release's mailfathom-schema-<version>.sql, apply it, and
let the rollout continue. {{ $documentationRoot }}operations/database-schema.html states the privileges it needs and
what each failure means.
{{ if .Values.database.deploy.enabled }}
The database is this release's own: a single-replica StatefulSet, its claim retained when the release is uninstalled.
The role MailFathom connects as owns its database and is not a superuser; the schema goes in through the server it runs:

  kubectl --namespace {{ .Release.Namespace }} exec -i statefulset/{{ include "mailfathom.postgresFullname" . }} -- \
    psql --username {{ .Values.database.user }} --dbname {{ .Values.database.name }} \
      --set ON_ERROR_STOP=on < mailfathom-schema-<version>.sql

Back it up the same way, with pg_dump, rather than by copying the volume's files. A store holding every synchronized
message eventually wants durability and an upgrade path that a claim does not provide by itself — set
database.deploy.enabled=false and name a server you operate when it does.
{{ end }}

The object store is this release's own: {{ if gt (int .Values.contentStorage.objectStorage.deploy.replicas) 1 }}a pool of {{ int .Values.contentStorage.objectStorage.deploy.replicas }} Silo pods, one claim each, whose width is fixed now rather than raised later{{ else }}one Silo node on one claim{{ end }}, retained when the release is uninstalled.
{{- if .Values.contentStorage.objectStorage.deploy.console.enabled }}
Its console is served, on a Service port no Ingress publishes: reach it with a deliberate port-forward, and know that
what authenticates at it is the root credential, which is the whole store rather than the one bucket.
{{- else }}
Its console is not served and no Service port routes to one.
{{- end }}

It ships no bucket and no access key, and this release creates neither, so both are provisioned once with the root
credential in {{ .Values.contentStorage.objectStorage.deploy.rootCredentialSecret }} — which MailFathom itself never
holds. Until the bucket answers and {{ .Values.secrets.existingSecret }} carries an access key scoped to it under
{{ .Values.contentStorage.objectStorage.accessKeyIdSecretKey }} and {{ .Values.contentStorage.objectStorage.secretAccessKeySecretKey }},
this deployment reports itself unready rather than storing mail. The `mcli` commands are in
{{ $documentationRoot }}operations/deployment-kubernetes.html.

Two stores now, so a pg_dump is no longer a whole backup: back the bucket up beside the database, and restore the
database first, or the reclamation sweep is entitled to delete objects nothing points at yet.
{{ end }}
{{ if and .Values.signalBackplane.enabled .Values.signalBackplane.valkey.deploy }}
The signal backplane is this release's own: {{ if .Values.signalBackplane.valkey.replication.enabled }}{{ add1 (int .Values.signalBackplane.valkey.replication.replicas) }} Valkey instances{{ else }}one Valkey{{ end }}, on no claim and keeping
nothing past a pod, because pub/sub keeps nothing. Every instance is started
with the password in {{ .Values.secrets.existingSecret }} under {{ .Values.signalBackplane.valkey.passwordSecretKey }},
and MailFathom reaches the endpoint with the connection string in the same Secret under
{{ .Values.signalBackplane.connectionStringSecretKey }} — which carries that same password:

  {{ include "mailfathom.backplaneFullname" . }}:{{ .Values.signalBackplane.valkey.service.port }},password=<the password above>
{{ if .Values.signalBackplane.valkey.replication.enabled }}
That Service names one instance — the one this set starts as the primary — because a publication travels from the
primary down to its standbys and never back up, so a connection handed to a standby would strand whatever MailFathom
published on it. Nothing promotes a standby: losing the primary is a `REPLICAOF NO ONE` you run against a replica and
that Service's selector repointed at it, and both last only until the next upgrade or pod restart puts the set back
into its rendered shape. What the standbys buy is an instance already running and in step when you do.
{{ end }}
Write both keys before you turn this block on. Neither pod starts without them: MailFathom proves the reference while
it builds and refuses to start when the mounted file is missing, and the kubelet cannot even create the backplane
containers without the password key, so a rollout begun without them cannot complete.

Once they are there, whether the server actually answers is a different matter and is not a reason to refuse anything.
An endpoint that is unreachable leaves the replicas fanning no signal out, and every client falls back on the re-read
it already does. Nothing reports that as unready: a signal is an optimization, and a pod pulled from service over one
is the worse outage. That is also the measure of what replication buys — a shorter gap, never a delivered signal.
{{ end }}
