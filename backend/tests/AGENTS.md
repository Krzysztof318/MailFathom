# Unit Test Instructions

These instructions apply under `backend/tests/` in addition to the repository root instructions.

The **.NET and C# conventions** in `backend/src/AGENTS.md` apply to test code as well. A test is C# compiled by the same build with the same analyzers, so naming, async shape, LINQ, disposal, and the rest hold here exactly as they do under `backend/src/`. The directory cascade does not load that file for a change under `backend/tests/`, which is why this line points at it.

## Unit testing policy

- Write or update the failing test before production code when practical.
- Use xUnit.net v3 on Microsoft Testing Platform v2 and NSubstitute for test doubles.
- Keep unit tests in projects named after the production boundary: `Domain.UnitTests`, `Application.UnitTests`, `Infrastructure.UnitTests`, `AI.UnitTests`, `Mcp.UnitTests`, `Host.UnitTests`, and `AppHost.UnitTests`.
- `SyntheticMail.UnitTests` follows the same naming for a boundary under `tools/` rather than `backend/src/`, because the development tooling there is built, analyzed, and formatted by the same gates as production code and is worth the same tests. What differs is only the coverage denominator: `.config/CodeCoverage.proj` measures projects under `backend/src/`, so nothing here counts towards the 85% aggregate, and `.config/testconfig.json` excludes the assembly so the gate's denominator check does not report one it never expected. Write the tests as if it did count — a seeded generator that stopped reproducing its corpus would break silently otherwise.
- `AppHost.UnitTests` covers the app model's own decidable logic — today the identifier every ephemeral container and volume is named from — and reaches it through a `Compile Include` rather than a project reference. A reference would inherit `Aspire.AppHost.Sdk`'s runtime-identifier-specific packages, and a project carrying those can hold no committed lock file, which is why `AppHost` and `IntegrationTests` are the only two without one. Compiling a source file that depends on nothing but the base class library keeps this project under that guarantee; a file that grows an Aspire dependency stops being testable this way, which is the signal that the logic belongs outside the app model.
- `Boundaries.UnitTests` is named after no production boundary because its subject is what holds between them, and it is the one project whose rules read compiled intermediate language rather than assembly metadata. Reach for it only where reflection structurally cannot answer the claim: a dependency that exists solely inside a method body, and a rule about a namespace within an assembly. Everything else stays where it is — `ApplicationDependencyBoundaryTests`, `McpDependencyBoundaryTests`, and `SecretBoundaryArchitectureTests` assert an *exact* reference set, which is the stronger assertion for that question because it puts a reference added for an ordinary reason in front of a reviewer instead of only refusing a forbidden one. Do not migrate them here and do not restate them here. A rule added here names the contract it holds in its `Because`, since that text is what a developer who trips it reads, and it names any type it has to admit rather than narrowing the rule until nothing is excluded. The suite is the slowest in the repository per assertion — loading eight assemblies' intermediate language costs about ten seconds once — so it holds a handful of rules about invariants worth that, not a rule per convention.
- `SharedSources.UnitTests` is the exception, because it covers the two directories no project owns: `backend/src/shared` and `backend/tests/shared`. Both are compiled into their consumers through `Compile Include` items, so this project compiles them the same way a consumer does and asserts their contracts in one place. The name is `SharedSources`, not `Shared`, because `Shared` is a reserved word in another .NET language and CA1716 rejects it as a namespace.
- `PublicSurfaces.UnitTests` is named after no production boundary either, because its subject is two of the four public surfaces [ADR 0004](https://github.com/Krzysztof318/MailFathom/blob/main/docs/decisions/0004-versioning-and-release-policy.md) governs. It renders the whole of each into a golden file committed beside it — `mcp-tool-contract.json`, which is every registered tool descriptor as a client discovers it, name, description, input and output schema, annotations and all; and `configuration-keys.txt`, which is every key an operator may write into a MailFathom configuration section, the type it binds as, and whether the section is refused without it. Neither file judges a change: a break is permitted below `1.0.0`, and what these exist to remove is the possibility of taking one without noticing. **A diff in either is a change to a public surface and obliges an entry in the release's changelog**, named against the surface it breaks and with the operator's action, which is what the release pull request composes `CHANGELOG.md` from. Regenerate a golden file with `MAILFATHOM_UPDATE_PUBLIC_SURFACES=1 dotnet test --project backend/tests/PublicSurfaces.UnitTests`, and commit the result in the change that moved the surface. The framework-shaped configuration sections are absent by design — `Logging`, `ConnectionStrings`, and the Kestrel endpoints are not MailFathom's — and so are the other two surfaces: the database schema is proven by `OrchestratedSchemaArtifactTests` against a real server, and the deployment contract by the assets that render it.
- Assert a shared marker attribute against a sample type declared beside its tests, not against whichever boundary applies it today. A marker compiled into several assemblies is a distinct type in each, so `IsDefined(typeof(...))` across an assembly boundary matches nothing and the assertion passes without inspecting anything. A local sample keeps the types identical; read the marker by name regardless, because that is how the coverage collector reads it.
- `Host.UnitTests` covers what the composition root decides: options validation rules, startup fail-fast behavior, hosted-service loops and their failure isolation, and the mapping from bound configuration onto infrastructure contracts. It does not build the real `WebApplication` and does not start a server — the request pipeline is the composed host's to prove, and the integration suite is where that happens.
- It does compose the real service graph, in `HostCompositionTests`, and that is the one place anything does. `HostComposition.Compose` is callable for exactly this reason, and the test builds a provider over it with `ValidateOnBuild` and `ValidateScopes` on and then resolves every service the MailFathom assemblies registered. The resolution is the point rather than the validation: the container sees through a constructor and not through a factory, most of what the composition root registers is a factory, and a service nobody registered behind one is otherwise first missed when a worker asks for it on somebody's server. Which registrations exist follows from configuration, so the test carries one shape per set of switches — an embedding chain, a chat endpoint and its relevance filter, each scanner, the spam daemon, the surfaces served — and a new switch that decides a registration takes a shape of its own in the same change. Health checks are walked beside the descriptors, because `AddHealthChecks().Add(...)` appends a registration to an options object rather than to the service collection: nothing the container does ever runs that factory, so a port it resolves that nobody registered would first be found by a probe answering in production. Nothing in it reaches a database, a socket, or the file system, and a registration that would is the finding rather than the test's problem to work around.
- Put logic worth unit-testing in `Domain`, `Application`, or `Infrastructure` rather than in `Host`. `Host.UnitTests` exists because some host-owned decisions are real, not as a licence to grow the composition root.
- Follow Arrange, Act, Assert. Add explicit `// Arrange`, `// Act`, and `// Assert` comments.
- A test helper needed by more than one boundary lives in `backend/tests/shared/` and is linked with a `Compile Include` item, the same arrangement `backend/src/shared/` uses. Keep such a file free of production behavior and give it the assembly-neutral `MailFathom.TestSupport` namespace.
- Name tests `Member_Scenario_ExpectedBehavior`. Use `[Fact]` for one scenario and `[Theory]` for the same behavior over multiple inputs.
- Test observable behavior and domain invariants, not private implementation details. One test describes one behavior even if several assertions prove it.
- Tests must be fast, isolated, repeatable, order-independent, and safe to run in parallel. Do not use real clocks, nondeterministic random values, shared mutable fixtures, sleeps, network calls, databases, containers, or the filesystem. A property test draws different inputs on each run and is the one bounded exception, on the terms *Properties and examples* below states.
- Prefer real domain values and simple in-memory fakes. Use NSubstitute at external or architectural boundaries where interaction is part of the contract.
- Never use the EF Core InMemory provider, SQLite in-memory, another in-memory SQL database, or mocked `DbSet` query behavior as a substitute for PostgreSQL semantics. Unit-test through application-owned ports and hand-written state fakes.
- Substitute the interface a library publishes rather than hand-writing a copy of it. MailKit publishes `IImapClient`, `IMailStore`, `IMailService`, and `IMailFolder`, so a test models a server's capabilities, responses, disconnects, and failures through those directly.
- Do not substitute a concrete client class such as `ImapClient`. Constructing one brings its real protocol machinery along, and only the members that happen to be virtual would be under the test's control.
- Write an own port only when it earns its existence: the library publishes no usable interface for the seam, the port carries behavior of its own, or it deliberately narrows a surface for a stated safety reason. Restating a published interface member for member is none of those, and the copy goes stale the moment the library moves.
- An application-owned port is a different thing and is still required at the boundary. `IMailboxSession`, `IMailboxSessionFactory`, and `IRemoteFolderCatalog` traffic in domain types and keep mail-library types out of `Application`; the library's own interfaces stay inside the adapter that uses them.
- Use `FakeHttpMessageHandler` from `backend/tests/shared` for anything that speaks HTTP. NSubstitute cannot supply it, because `HttpMessageHandler.SendAsync` is protected and no substitute can override it, so the handler is hand-written and shared instead of duplicated per project. Do not add a third-party HTTP mocking package, and do not stand up a local HTTP server; a real server belongs to the future integration suite.
- Cover everything in `backend/tests/shared` from `SharedSources.UnitTests`, because a fault in a shared helper reports a false result in every suite that uses it rather than failing where the fault is.
- Use `Received()` and `DidNotReceive()` only when the interaction is a required side effect or safety invariant. Use argument matchers only while configuring substitutes or verifying calls.
- Build test data with LINQ projections such as `Enumerable.Range(...).Select(...)`, and assert against a projected sequence instead of looping to compare element by element; a failing `Assert.Equal` over two sequences reports both, while a loop reports only the first mismatch. Configuring a substitute or verifying `Received()` per element is a side effect and stays a loop, including when the per-element work is extracted into a factory method: `Substitute.For<T>()` and `Returns` write to NSubstitute's ambient call context, not only to the object handed back, so deferred execution could interleave one substitute's setup with another's.
- Every IMAP content-fetch path must prove that no operation capable of setting `\Seen` was requested.
- **A test never calls a paid provider by default.** Calling an AI provider is what costs MailFathom money per unit of mail, so a suite that spends the maintainer's credit on every run is one nobody can afford to run — and making it the default would spend a contributor's too. A test that reaches a real provider is written with xUnit v3's `SkipUnless` on a public static property reading `AiProviderContractRun.Requested`, which reads an environment variable nothing sets, so a developer's run and an ordinary pipeline run both cost nothing; the `Integration tests` workflow turns it on through an input that defaults to off and supplies the credentials with it. That switch is one for the whole AI boundary rather than one per provider: which half of it a test spends against is not a distinction the operator turning them on makes, and a second switch would mean a provider added later runs free by default until somebody remembers it exists. `Skip` carries the message that conditional skip reports, and it is required rather than decorative: xUnit reads it before it reads the condition, so an attribute setting `SkipUnless` without it fails the test on every run — including the runs the condition was written to make free — and neither the analyzers nor the published API documentation says so. Asking for such a run without a credential configured **fails** rather than skipping, because a run somebody explicitly requested and which then quietly proved nothing is worse than one that never started. Write one or two such tests per adapter and no more: they prove the protocol, the authentication, the failure classification against real responses, and the shape of the answer, and everything else belongs on the free path — against a real database and a deterministic in-repository generator. `backend/tests/IntegrationTests/ProviderAdapters` holds every such test, `EmbeddingProviderContractTests` and `ChatProviderContractTests` are the worked examples, and [ADR 0006](https://github.com/Krzysztof318/MailFathom/blob/main/docs/decisions/0006-embedding-profile-identity-lifecycle-and-activation-cost.md) holds the reasoning.
- **A test that reaches a real provider is retried, and only that kind of test is.** Write it with `[RetryFact]` from `xRetry.v3` in place of `[Fact]`, over a bounded number of attempts and a delay between them, both named as constants on the class rather than repeated as literals. The attribute derives from `FactAttribute` and its discoverer forwards the skip through unchanged, so `Skip` and `SkipUnless` are set on it exactly as the rule above requires and the free run stays free. A hosted provider answers `429` when a key or a tenant briefly exceeds its rate limit and `529` when the service is overloaded; both are transient by construction and neither is about the protocol, the authentication, the failure classification, or the shape of the answer such a test exists to prove. Reporting one as a failure says the adapter is wrong when the provider was busy, and the only remedy left is a hand-dispatched rerun of a suite that starts a container to reach two tests. What the attribute buys is bounded and stated: it cannot tell a rate limit from a wrong answer, so a genuine failure is re-run before it is reported, which is worth a few seconds and a handful of short calls here and is worth nothing where the failure would have been a defect. That is why the licence stops at the provider boundary — a test against the orchestrated database, the orchestrated mailbox, or a composed host is talking to infrastructure this run started, and retrying one there would hide the fault it was written to find.
- Cover cancellation, retry boundaries, idempotency, duplicate events, UIDVALIDITY changes, partial failures, and unsafe TLS or authentication configuration where relevant.
- Run the complete unit test suite before committing.

## Properties and examples

An example test fixes an input and asserts the output. A property states what has to hold for *every* input in a domain and lets a generator hunt for the one that breaks it, which is the one thing an example cannot do — the defects that reached production here were not on uncovered paths but on inputs nobody thought of. The two are not alternatives and neither replaces the other: a property covers a rule and an example covers a case, and where a change touches both, both move.

- **Write a property when the subject is pure and deterministic and the claim is about a domain rather than a case.** The shapes that qualify are the ones a rule can be written down for: an encode and decode pair that has to return what it was given, a cut whose parts have to cover what they were cut from, an ordering that has to advance, a calculation that has to agree with the reading that walks it, and an absence guarantee such as *a detected value never leaves in the text*. `KeysetCursorPayloadProperties`, `DeterministicEmailTextChunkerProperties`, `JobRecurrenceProperties`, and `SensitiveContentRedactorProperties` are the worked examples.
- **Write an example when the value itself is the contract, or when the input is a case rather than a domain.** A recorded encoding a client is part-way through, a failure path and the exception it raises, an argument guard, a branch a substitute decides, an input that once broke and must not break again, and everything a property leaves free — a property that says a boundary advances says nothing about *where* it lands, and an example is what pins that. An example that a property now generalizes stays where it is; deleting it loses the case.
- **Never generate over anything impure.** A property that reaches a database, an IMAP session, a provider, or the file system multiplies that cost by the iteration count until the suite is no longer runnable, and the point of generation is inputs rather than round trips. Where the behaviour lives behind such a boundary, extract the decidable part and state the property over that.
- **A property is stated once and run through `PropertyCheck`,** which fixes the thread count and the reproduction contract for every suite at once. Do not call the generator's own sampler except to assert something about that contract itself.
- **Name it so the failure reads as the rule that broke,** under the same `Member_Scenario_ExpectedBehavior` shape as any other test, with the domain in the scenario and the invariant in the expectation: `DeriveChunks_AnyTextAndAnyRuleSet_ReadsEveryPassageBackFromItsOwnOffsets`. Put the properties for a subject in a class named after it and ending in `Properties`, beside the `Tests` class covering the same subject, and give the class one iteration-count constant rather than a literal per property.
- **The iteration count is a budget rather than a target.** Draw enough inputs that the interesting shapes arrive and few enough that the whole set stays inside the ordinary unit-test run; a few hundred is the working range, and lower where an iteration runs an asynchronous operation.
- **A property must be true of every input its generator can produce.** That is what pays for the exception to the repeatability rule above: generation is seeded per iteration but the run is not pinned, so a property that is only usually true fails on somebody else's pull request for something they did not write. When one does, the fix is the property or the generator, never a re-run — and a generator that has to exclude an input is stating a real precondition, which belongs in the class remarks beside it.
- **Reproduce a failure from the seed it names.** The failure reports the shrunk input, the reason, and a seed; re-running with `CsCheck_Seed` set to it replays that one case. Report the seed in a bug report or a pull request, because nothing else makes the case reachable again.
- **Prove a property is not vacuous before committing it.** Break the rule in the production code, watch the property fail, and put the code back. A property over a generator that never produces the interesting shape passes forever and reads exactly like one that works, and it is the failure mode this kind of test has that an example does not.

## Code coverage

- Maintain at least 85% aggregate line coverage across every project under `backend/src/` except `Host` and `AppHost`.
- Calculate the threshold across the complete configured codebase, never from patch, changed-line, or per-project coverage.
- Keep `Host` and `AppHost` excluded as thin composition roots. Do not add other exclusions merely to pass the threshold.
- The exclusion is about the coverage denominator, not about testing. `Host.UnitTests` and `AppHost.UnitTests` run in the same suite and their assertions are as binding as any other project's; their subjects simply do not count towards the aggregate, because a composition root's uncovered wiring would otherwise dilute the measurement of the boundaries that hold the logic.
- Give a project whose `AssemblyName` does not begin with `MailFathom.` an entry of its own in the Coverlet `Include` filter in `.config/testconfig.json`, which matches by assembly name. Forgetting is caught rather than trusted: `.config/CodeCoverage.proj` fails the coverage target when a measured project's assembly is missing from the merged report, so an assembly cannot leave the gate without the gate saying so.
- Add `using System.Diagnostics.CodeAnalysis;` and apply `[ExcludeFromCodeCoverage]` only to a class with no executable application, domain, mapping, validation, policy, or infrastructure logic.
- Add `using MailFathom.CodeCoverage;` and apply `[RequiresIntegrationCoverage]` to a class or member whose behavior is real but can only be proven against a real database, a real mail server, or a composed host. The two attributes answer different questions: `[ExcludeFromCodeCoverage]` says the code never participates in coverage, `[RequiresIntegrationCoverage]` says the verification lives in the integration suite, which collects no coverage of its own. Choosing the accurate one keeps the reason for an exclusion readable years later.
- The marker is declared once in `backend/src/shared/RequiresIntegrationCoverageAttribute.cs` and compiled into each project that applies it through a `Compile Include` item, because the collector matches it by name rather than by declaring assembly. Add that item when a second project needs the marker; do not reference a project for it.
- Never exclude meaningfully testable behavior with either attribute. Business logic, mapping, validation, and policy stay in the denominator, and needing a marker to reach the threshold means the test is missing, not the exclusion.
- Remove the exclusion and add coverage when unit-testable logic enters an excluded class. `[RequiresIntegrationCoverage]` survives the arrival of the integration suite, and survives the class being covered by it, because integration runs never feed the unit-test metric and the marked code stays unreachable from a unit test either way; `[ExcludeFromCodeCoverage]` is removed as soon as executable logic appears.
- Run `dotnet msbuild .config/CodeCoverage.proj -t:Collect` before committing production or test changes.

## Cost claims

A claim that a path is cheap belongs in one of two places, and which one is decided by whether the claim can be checked rather than by how much it matters. Writing it in the wrong one produces either a gate that fails for reasons nobody controls or a number nobody ever reads.

- **What a path allocates is a test, and it gates every pull request.** `backend/tests/AllocationBudgets.UnitTests` holds those budgets. Allocated bytes are counted rather than timed, so a loaded runner moves nothing, and the deployment runs under a container memory limit where an allocation regression on a large message is an `OOMKill` rather than a slower answer. A new budget goes there beside the four already written — MIME extraction, an attachment download, a content-store read, and chunking — rather than into the suite of whichever boundary owns the path, because a budget is one claim made the same way about several boundaries and the reasoning is only readable with the others beside it.
- **What a path costs in time is a report, and it gates nothing.** `backend/tests/Benchmarks` measures it with BenchmarkDotNet and runs from `nightly.yml`, where a failure is swallowed and no job waits on the result. It is a project under `backend/tests/` that is not a suite: `.config/CodeCoverage.proj` keeps it out of the projects the coverage target runs and `.config/testconfig.json` excludes its assembly, the same two-part mechanism that keeps `tools/SyntheticMail` out of the denominator.
- **No timing assertion is ever a gate**, here or in the integration suite or in any pull-request check. A hosted runner is shared and virtualized, so an elapsed time measured on one says nothing reproducible about the next; a threshold over it fails on a busy neighbour and passes on a quiet one, which is a flake wearing the clothes of a performance guarantee.
- **A budget is a ceiling, never a number.** Set it with room for a runtime that sizes a buffer differently, and state in the constant's own documentation what it is a share of and which regression it fails. Do not tighten one to whatever the last run happened to produce, and do not lower one in the same change that made a path cheaper — a bound exists so a regression fails, and the two acts look identical in a diff.
- **Both forms measure the same message.** `LargeSyntheticMessage` in `backend/tests/shared` composes it from the repository's own deterministic generator, so a budget stated as a share of its length and a throughput number taken over it stay comparable. A measurement that composed a message of its own would be a second answer to what a large message is.

## Integration tests

The boundary between the two kinds of test is what a test is allowed to depend on, not where the behavior lives. A unit test stays free of the network, containers, a database, and the file system, as the policy above requires. Everything that needs one of those — EF Core mappings, migrations, LINQ translation, raw SQL, transactions, concurrency, PostgreSQL full-text search, pgvector, `bytea`, database constraints, and MailKit wire behavior against a real server — belongs to the integration suite and must not be mislabelled as a unit test.

- `backend/tests/IntegrationTests` is the one integration-test project, and it stays the one. It is not named after a production boundary, because it verifies how the boundaries behave together against real infrastructure rather than any single one of them.
- The suite starts the repository's own app model through `Aspire.Hosting.Testing` rather than defining containers of its own, so what it verifies is the orchestration a developer runs. `MailFathomOrchestrationFixture` is an assembly fixture: one PostgreSQL container for the whole suite, and a test isolates itself through the data it writes rather than through infrastructure of its own.
- The app host is started with the argument `IntegrationTesting=true`, which selects the ephemeral topology: every container and volume is named with a shared prefix followed by an identifier for that run, so a killed run leaves something identifiable while two runs on one machine collide over nothing and neither removes the other's resources; and the MailFathom host resource is present but does not start with the application. Most tests exercise classes against a real database and a real mailbox and own both exclusively; a second MailFathom reconciling folders underneath them would make its synchronization part of every one of those tests' environment.
- The composed host is started on request, by `MailFathomOrchestrationFixture.StartMailFathomHostAsync`, and only from `ComposedHostCollectionDefinition` — a collection `ComposedHostsRunLastCollectionOrderer` places after every other. Ordering is the whole isolation mechanism here, so a test that needs the composed host joins that collection rather than starting the resource from somewhere else. Under that topology the app model switches synchronization off and configures the MCP endpoint with a key and a narrowed origin list, so what the started host exercises is its request pipeline rather than its workers.
- A second composed host, `mailfathom-mtls-host`, is served over HTTPS behind a `Required` client-certificate profile, started by `StartMutualTlsHostAsync` from `MutualTlsHostCollectionDefinition`, which the same orderer places after the collection above. It is a second resource rather than a posture on the first because a certificate requirement is one answer for a whole process: the host above is reached without a certificate by every test written about a credential, an origin, or a limiter. It is a second collection because starting it is a second project process, and the collection before it measures a rate limit that a busier machine changes. Its certificates are issued per run by `OrchestratedMutualTlsCertificates` from the shared `TestCertificates` and injected into the environment variables the app model's secret references name, so no private key, certificate, or trust anchor is committed. Reach for it only for what a certificate on a real TLS connection can establish and a substitute cannot.
- Reach for the composed host only for what a class-level test structurally cannot reach: that middleware is wired into the pipeline in the right order, that a route carries the metadata it was given. Behavior below that — which credentials authenticate, which origins are served — is unit-testable and belongs in the unit suite, where it is already covered.
- A third host is started **inside the test process**, by `InProcessComposedHost`, and it is the one MailFathom the app model does not configure. What it reaches is the half of the pipeline that is decided while a host starts rather than by the code composing it: minimal hosting runs routing in front of the application's middleware, appends endpoint execution behind it, and inserts an authentication and an authorization middleware of its own wherever the application added none — so the order a request actually meets exists in a started host and nowhere else. Driving it needs a deployment shape per test, both surfaces authenticating and one and neither, which a process the app model configured once cannot be asked for. It binds no socket, keeps none of the workers the composition registered, and touches neither the orchestrated database nor the orchestrated mailbox; it joins the composed-host collection for that collection's ordering rather than for its fixture. Reach for it only for what the assembled order proves, and leave which schemes a shape registers to `HostCompositionTests`, which composes the same graph without starting it.
- The suite collects a coverage report of its own, and it is informational. It never merges into the aggregate the 85% gate reads and it enforces no threshold, so unit tests stay the only source of an enforced metric and an expensive suite never has to run to know whether the gate passes.
- The two reports ask opposite questions of the same attribute, which is why they need separate collector configurations. `.config/testconfig.json` excludes everything marked `[RequiresIntegrationCoverage]` because a unit test cannot reach it; `backend/tests/IntegrationTests/testconfig.json` does not, and `scripts/run-integration-tests.sh` narrows the report to exactly the files carrying the marker. The filter is derived from the marker by searching for it, so a newly marked class enters the report without a second list being edited.
- The marker stays once a class is covered, as the rule above already says. It records where a class's verification lives, not whether that verification has been written yet, and a class that is structurally unreachable from a unit test stays unreachable after its integration test exists. Removing it would drop the class out of this report and into the unit denominator at nearly zero, so a new integration test would lower the enforced metric and hide the coverage it just produced. Progress is read from this report's percentage rising, not from markers disappearing.
- It runs only when asked, through `scripts/run-integration-tests.sh`, and in continuous integration only through the manually dispatched `Integration tests` workflow. `IsTestingPlatformApplication` is set to `false` for the project, which is what keeps a solution-wide `dotnet test` — the fast loop and the coverage gate — from discovering and starting it. The project stays in `MailFathom.slnx` regardless, so it is built, analyzed, and formatted by the same gates as everything else.
- Do not add Testcontainers, a second Docker fixture, or a parallel container topology beside the app model. A dependency a test needs is added to the app model as an ordinary resource, under the same ephemeral naming.
- **A resource is reached through the orchestration's endpoint proxy, which relays bytes and not a connection's shape.** That is what keeps a container's port random and a run's topology ephemeral, and it costs one thing worth knowing before a protocol is exercised through it: a half-close does not survive the relay. A client that shuts its own write half down to say it has finished sending gets no answer back and no failure either — the read ends at once and empty, so the exchange reads as a peer that answered nothing rather than as a connection that was torn down, and a loop written around it waits forever. Nothing here reproduces the trap in a unit test, because it is a property of the path rather than of either end. So a protocol reached this way states its own lengths, which is what `SpamAssassinDaemon` does with `Content-length` and what `MailFathomOrchestrationFixture`'s readiness ping does by needing no body at all; a protocol that genuinely cannot works only against an endpoint the app model declares unproxied, and that pins the host port for the whole machine.
- **A fixture that seeds mail directly runs no account run, so what it writes is a message at the point the storing transaction leaves it: text, a search document, no passages, and no rule-evaluation stamp.** Everything an account run performs afterwards is a step a test asks for by name — `OrchestratedPassages.CutAsync` for the cut, `OrchestratedRuleEvaluationStamp.ApplyAsync` for the stamp — through the production store, so that what a test arranges is a row shape a deployment produces rather than one only a harness can. Two things follow. A test needing settled mail says so instead of inheriting it, and a class whose helper stops matching the pipeline fails as emptiness — no passage, no vector, no candidate — in every test of that class at once. And a claim over the whole shared database is stated against what the pipeline can reach rather than as a plain zero: every other class in the collection leaves uncut, unstamped mail behind, so "this sweep left nothing outstanding" is measured against that group instead of asserting it is empty.
- **A UID names an occurrence, so two tests of one class that store the same UID in one folder write one row rather than two.** `(account, folder, UIDVALIDITY, UID)` is the remote identity the store upserts on, and the second write therefore finds whatever the first test left on the row — an evaluation stamp above all, which takes the message out of the arrival queue before the second test has read it. Give each test its own numbers, from a block the class's other tests do not use.
- **A use case published to a caller is reached under one, and nothing here supplies a caller by default.** This suite starts no request, so `StatedAuthorizedPrincipalSource` answers with the process identity — which is what a worker runs as and what `RequireProcessIdentity` admits. Every use case published to an agent or an operator refuses that outright, so a test driving one states the caller for its own scope with `OrchestratedMailFathomServices.AsCallerInScopeAsync` and names exactly the permissions the act is published under; `InScopeAsync` stays for the work MailFathom performs for nobody. Two things follow. The grant is part of the arrangement rather than a formality, so a permission renamed, split, or narrowed leaves the test refused rather than green, and the refusal arrives as `PrincipalNotAuthorizedException` from whatever line the class happened to reach first. And a class whose helper reaches the use case through the wrong one fails in every test at once, which is what the last provider-contract run found across five classes at the same time.
- **A folder a test binds is a folder `SyntheticMailAccount.MappedFolderAliases` names.** A read model resolves its scope through that list before it reads a row, so a binding committed under an alias the list omits is stored and then invisible: the row is written, the timeline answers with nothing, and the assertion reports the query as broken. The list is also what makes a folder a test's own — a queue read is answered per folder rather than per UID, so a second test storing into this class's folder is reported by the first one whenever the order puts it there, and distinct UIDs do not help. Add the alias with the test, and give a test whose claim is about what a folder holds a folder of its own.
- **The composed host's configuration is validated when it starts, and a block that fails validation reaches a test as a request that never answers.** The app model configures that process, so an option it writes wrongly — a secret block stating a reference and no name is the one this suite has met — stops the host before it binds a socket, and the suite's client then waits out its own hundred-second timeout on every route the class names. A composed-host class failing entirely on `TaskCanceledException` is therefore read as the host having failed to start, and the cause is in the resource's own output rather than in the assertion; nothing in the timeout says which option it was.
- **The composed host runs the delivery worker, so a send it queues is claimed before the next tool call arrives.** `OutboxDeliveryWorker` is registered on every deployment and answers the signal an enqueue raises, so a tool call that answers with a queued identifier is followed within milliseconds by a claim that holds a lease no withdrawal may write through. What the topology gives that claim is a submission host in the reserved testing domain that resolves nowhere: the attempt fails as a transport failure, which defers the send rather than ending it — the stage moves back to recorded, the lease is released, a failure code is written, and the record is withdrawable again until `OrchestrationContract.ComposedHostDeliveryRetryDelay` elapses, which is longer than a run. So a class asserting anything about a queued send other than the record a call answered with waits for that failure code to appear rather than reading straight after the send, and the answer a sending tool returns is a snapshot taken at commit and is safe to assert on directly.
- **The composed host reads its own configuration and none of the harness's ports.** `SyntheticMailAccount` supplies the accounts and folder mappings to the services a persistence test composes in process; the started host resource is a separate process configured by the app model, so a folder it has to serve is mapped there, in `Program.cs`, under the alias `OrchestrationContract` declares. A readable scope is composed from mappings rather than from what the store holds, so a host mapping no folder answers a tool call with an empty window over mail the same run stored — which reads as the tool being wrong rather than as the deployment having no such folder.
- **An idempotency claim is proved by running the operation concurrently, and a sequential repeat proves the half nobody doubted.** Synchronization, object writes, and outbox processing are all required to be idempotent, and calling an operation twice in sequence establishes only that the second caller recognizes what the first committed. What a deployment does is call it twice at once, from two workers, where neither can see the other's uncommitted write and the application's own read-before-write answers nothing — so the effect is decided by a unique index, a locking clause, or a conditional update, and by nothing a substitute could stand in for. Such a claim is written with `ConcurrentIdempotency.RunAsync` in `backend/tests/IntegrationTests/Orchestration/`, which runs one operation from N callers at once and hands back a `ConcurrentAttempts<TResult>`; the test then states its single effect through `AssertSingleEffect`, as a count rather than as a presence, so a partial duplicate fails as the number of effects the operation left. N is a constant of the calling class, large enough that a caller reliably loses — a pair can be serialized by the scheduler alone — and small enough that the claim costs the suite seconds. Nothing orders the attempts and nothing may: a scheduler or an injected barrier would establish that the operation is idempotent under the one interleaving the harness chose, which is the opposite of the claim. An attempt that throws is one of the outcomes rather than an error of the run, because a duplicate refused by a unique index is how the database enforces several of these; a run where every attempt failed is the one case that fails on its own, since the single effect was then left by the arrangement. `backend/tests/IntegrationTests/Idempotency/` is where such a class goes, named after the invariant rather than after a boundary because one class holds the claims of several, and `OrchestratedConcurrentIdempotencyTests` is the worked example.
- Fixtures use synthetic mail data only. No real mailbox, real credential, or real personal data enters the repository, and the suite never points at a developer's or an operator's database.

### How many, and in what order

**The program behaving correctly outweighs what this suite costs to run.** An integration test does cost container start-up, real I/O, and continuous-integration minutes on every run, and it costs them again on every rerun of a flake. That is a real cost and it is the smaller one: what this suite exists for are the defects that surface as nothing at all — a total that stops adding, a query that recognizes none of its own rows, a ranking whose two halves stop agreeing on which message they are ranking — and every one of those reaches an operator as a wrong answer or a wrong invoice rather than as a failure. Where the minutes and the proof pull against each other, write the test. The rules below bound how a test is arranged, not how many the suite may hold.

- Write the test whose failure would otherwise be silent, and do not weigh it against the suite's runtime. What still decides where a test belongs is what it would establish: a rule a substitute already exercises — a branch, a mapping, a validation, an argument guard — belongs in the unit suite, because a substitute settles it and settles it faster, so putting it here makes the suite slower without making the program safer. That is a placement rule rather than a budget, and a class with six claims only real infrastructure can settle earns six tests. Prefer one test that covers several operations of the same session or the same run over several that each pay for their own composition, and split where the failures would otherwise be indistinguishable — which is about a failure being readable, never about a count. A dozen tests on one class is worth reading twice rather than refusing: usually it means unit-testable logic has been pushed here, occasionally it means the class really does hold a dozen such claims.
- **One cost this does not relax is a provider's.** A test that reaches a real AI provider stays behind the single switch the unit-test policy above describes, defaults to spending nothing, and stays at one or two per adapter; ADR 0006 is the decision, and what bounds it is somebody's credit rather than a pipeline's minutes. Everything downstream of that boundary — the schema, the workers, the ranking, the retrieval a model is handed — is provable for nothing against the in-repository deterministic generator, so the free path is where a new claim about the AI boundary goes.
- Put every test that shares a resource into one collection and turn its parallelization off. Shared here means the orchestrated PostgreSQL database and the orchestrated mailbox, neither of which can be isolated per test: the mailbox has one inbox whose UIDs advance globally, and a folder one test recreates changes what another would select. `OrchestratedInfrastructureCollectionDefinition` is that collection, declared with `DisableParallelization = true`, and a test class joins it with `[Collection(OrchestratedInfrastructureCollectionDefinition.Name)]`. Declaring the collection is preferred to switching parallelization off for the whole assembly, because it states which resource is shared and leaves a future test that shares neither free to run alongside.
- Ordering is allowed in this suite and nowhere else, at two levels. Collections are ordered by the assembly's `ITestCollectionOrderer`, which states two constraints — a composed host runs after the infrastructure tests, and the mutual-TLS host runs after the other composed host — and leaves everything else in the order xUnit produced. All three collections disable parallelization, which is what makes that ordering mean anything: xUnit runs collections that disable it sequentially, after the parallel-capable ones. Within a class, ordering test cases is allowed for the reason below.
- Ordering test cases inside a class is allowed in this suite and nowhere else. Some of what synchronization has to guarantee is a claim about a second run rather than a first — that synchronizing a folder again stores nothing twice — and collapsing that into one test reports the second run's failure against arrangement code, while leaving two tests unordered lets whichever ran first decide what the other found. Express the order with `[TestCaseOrderer(typeof(MailboxStateSequenceOrderer))]` on the class and `[MailboxStateStep(n)]` on each test that genuinely reads state an earlier one produced. A test that needs no step carries none and runs after those that do. Ordering is a licence for a seeding step followed by a reading step, never a way to let unrelated tests leak state into each other.
- An assertion that a flag, a row, or a side effect is absent proves nothing unless the same observation would report it present. Where a test asserts an absence — above all the remote `\Seen` invariant — the class also carries the control that produces the thing and observes it, so a server or an observation channel that silently reports nothing fails loudly instead of passing everything.
